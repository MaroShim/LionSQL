## 1. 배경과 현재 상태

- 앱 연동(Gitea, IOTA, Grafana, Casdoor 등)은 "기동과 기본 기능"까지만 보증한다. 장시간 안정성과 크래시 복구는 별개 영역이다.
- 현재 크래시 관련 테스트는 `pkg/storage/memengine/wal_test.go` 정도이며, 실제 프로세스를 강제 종료하는 엔드 투 엔드 검증은 없다.
- 보유 자산: TPC-C 부하 도구(`cmd/tpcc_runtime`, `cmd/tpcc_client`, `cmd/tpcc_kernel`), Prometheus `/metrics`, WAL/AOF, WiredTiger 체크포인트, 데이터 무결성 결함 107건 아카이브.

## 2. 지켜야 할 내구성 계약 (검증 대상)

| 번호 | 계약 | 설명 |
| :---: | :--- | :--- |
| D1 | 커밋 내구성 | 클라이언트가 `COMMIT` 성공 응답을 받은 트랜잭션은 크래시 후 반드시 존재한다 |
| D2 | 원자성 | 커밋되지 않았거나 중간에 끊긴 트랜잭션은 부분적으로도 보이지 않는다 |
| D3 | 일관성 | 복구 후 PK/유니크 제약, 인덱스와 테이블 내용이 일치한다 |
| D4 | 복구 가능성 | 어떤 시점에 죽어도 재기동이 성공하거나, 실패하면 명확한 오류로 중단한다(조용한 데이터 손상 금지) |
| D5 | 장기 안정성 | 장시간 운영에서 메모리, 핸들, 디스크 사용량이 유계이며 성능이 열화되지 않는다 |

> 스토리지 엔진별 내구성 수준이 다르다(예: In-Memory OCC는 WAL/AOF 설정에 따라 마지막 몇 ms 손실이 설계상 허용될 수 있음). 엔진과 fsync 정책별로 D1의 기대치를 표로 명시하고, 테스트는 그 기대치를 기준으로 판정한다. (1단계 산출물)

## 3. `DURA-KILL-1` 킬 테스트 (크래시 복구)

### 3.1. 무엇을 하는가
부하를 걸어 둔 서버를 무작위 시점에 강제 종료하고, 재기동 후 "클라이언트가 확인한 것"과 "DB에 남은 것"을 대조한다.

```
[워크로드 클라이언트] --(트랜잭션 + 성공 응답을 로컬 장부에 기록)--> [LionSQL]
        |                                                            |
        |                        무작위 시점 kill -9  <--------------+
        v                                                            v
   장부(ack 목록)  ------------ 재기동 후 대조 ------------>  복구된 DB 상태
```

### 3.2. 한 번의 반복(라운드)
1. 빈 데이터 디렉토리로 서버 기동.
2. N개 동시 연결로 쓰기 워크로드 시작. 각 트랜잭션은 고유 ID와 체크섬 가능한 내용을 쓰고, `COMMIT` 응답을 받으면 **클라이언트 측 장부 파일에 즉시 기록**(`ack` 목록).
3. 0.5~30초 사이 무작위 시점에 서버에 `SIGKILL` (정상 종료 경로 우회).
4. 서버 재기동. 복구 시간 측정.
5. 오라클 검사:
   - **D1**: 장부의 모든 `ack` 트랜잭션이 DB에 존재하고 내용이 일치.
   - **D2**: 다중 행 트랜잭션은 전부 있거나 전부 없음(예: 계좌 이체의 차변/대변 합계 불변).
   - **D3**: PK/유니크 위반 없음, 인덱스 경유 조회와 풀스캔 결과 일치, TPC-C 일관성 조건(주문/주문라인 개수, 재고 합계 등).
   - **D4**: 재기동 성공 여부와 소요 시간. 실패 시 오류 메시지가 명확한지.
6. 같은 데이터 디렉토리로 다음 라운드 계속(누적 크래시). 실패 시 데이터 디렉토리와 장부를 보존해 재현 가능하게 저장.

### 3.3. 변형 시나리오
| 시나리오 | 내용 | 노리는 결함 |
| :--- | :--- | :--- |
| 체크포인트 중 킬 | 체크포인트/컴팩션 진행 중 `SIGKILL` | 체크포인트 경계 불일치 |
| DDL 중 킬 | `CREATE/DROP/ALTER TABLE`, 인덱스 생성 중 `SIGKILL` | 카탈로그와 데이터 불일치 (`BUG-PITR-DDL-*` 계열) |
| 연속 킬 | 복구 직후(복구 중 포함) 다시 `SIGKILL` | 복구 멱등성 |
| WAL 꼬리 손상 | 서버 정지 상태에서 WAL 끝을 잘라내거나 바이트 손상 후 기동 | 손상 로그 감지, 조용한 오복구 방지 |
| 디스크 가득 참 | 용량 제한 파일시스템에서 쓰기 | 오류 전파, 부분 쓰기 |
| 정상 종료 대조군 | `SIGTERM` 후 재기동 | 정상 종료 경로 회귀 (Rule 4: 1.5초 내 종료) |

### 3.4. 구현 방향
- 위치: `cmd/crashtest/`(오케스트레이터: 서버 기동/종료, 장부 대조)와 `scripts/`.
- 서버는 별도 프로세스로 실행(`exec.Command`, 인자 벡터 직접 전달: Rule 3). 테스트는 `time.Sleep` 대신 포트 준비 폴링과 컨텍스트 타임아웃으로 동기화(Rule 17).
- 장부 파일은 임시 파일 + 원자 rename으로 갱신해 클라이언트 측 손실을 배제(Rule 1).
- 엔진 매트릭스: In-Memory OCC(WAL/AOF), WiredTiger. 프로토콜은 PGWire 우선, TDS는 후속.
- 결과: 라운드 수, 실패 라운드, 위반된 계약 번호, 재현용 아티팩트 경로를 요약 리포트로 출력. 위반 1건이라도 종료 코드 비정상(Rule 22).

### 3.5. 완료 기준
- 각 엔진에서 연속 5,000 라운드 위반 0건, 모든 시나리오 변형 통과.
- 발견 결함은 `BUG_ARCHIVE`에 기록하고 회귀 테스트로 승격.

### 3.6. 크래시 복구 도구(`cmd/crashtest`) 구현 및 20라운드 실측 결과 (2026-10-31)
- **구현 내용**:
  - 다중 워커 계좌 이체(`crash_accounts`) + 커밋 장부(`crash_ledger`, SHA-256 체크섬 검증) + 동시 DDL(`CREATE/DROP TABLE`) 워크로드 및 4단계 정합성 오라클(D1 커밋 내구성, D2 원자성 `SUM(balance) = 200,000`, D3 PK/체크섬 일관성, D4 복구 가능성) 구현.
  - 변형 시나리오(`SIGKILL`, `SIGKILL+DOUBLE_KILL` 연속 강제 종료, `SIGKILL+TORN_WAL_TAIL` WAL 꼬리 절단 손상 복구, `SIGTERM` 정상 종료 대조군) 자동 실행 지원.
- **발견 및 수정한 결함 3건**:
  1. **WiredTiger 유저 공간 로그 버퍼 유실 (`pkg/storage/wiredtiger/wt_engine.go`)**: 기본 설정에서 `commit_transaction` 직후 `SIGKILL` 수신 시 WiredTiger C 유저 공간 로그 버퍼에 남아 있던 커밋 레코드가 유실되던 문제를 해결하기 위해 `wiredtiger_open`에 `transaction_sync=(enabled=true,method=none)`을 적용하여 커밋 시 OS 파일시스템 버퍼(`write(2)`)로 즉시 플러시되도록 수정하고, `saveCatalog()`에 임시 파일 + 원자적 `os.Rename`(Rule 1)을 적용.
  2. **PGWire 텍스트 파라미터 과학적 표기법 오인 (`pkg/wire/server.go`)**: `'e'`를 포함한 16진수 체크섬 문자열(예: `"83920194837261e2"`)이나 선행 0 숫자 문자열이 `strconv.ParseFloat` / `strconv.ParseInt`에 의해 부동소수점(`Inf`)이나 정수로 잘못 변환되던 문제를 `isPureIntegerString` / `isPureFloatString` 가드로 해결.
  3. **`CREATE TABLE` 제약 조건 접두사 충돌 (`pkg/engine/sqlexec_ddl.go`)**: `strings.HasPrefix(cUpper, "CHECK")` 및 `"UNIQUE"`, `"CONSTRAINT"` 단순 접두사 비교로 인해 `checksum`, `checked_at`, `unique_id` 등의 컬럼 정의가 테이블 제약 조건으로 오인되어 스키마에서 누락되던 버그를 토큰 경계 검사로 수정.
- **엔진별 20라운드 실측 결과**:
  - **In-Memory OCC (`-engine memory -rounds 20`)**: `20/20 PASS` (`SIGKILL`, `SIGKILL+DOUBLE_KILL`, `SIGKILL+TORN_WAL_TAIL`, `SIGTERM` 전 시나리오 통과, 총 `64,214`건 커밋 트랜잭션 100% 복구, 복구 시간 `42ms~282ms`, 위반 `0`건).
  - **WiredTiger (`-engine wiredtiger -rounds 20`)**: `20/20 PASS` (`SIGKILL`, `SIGKILL+DOUBLE_KILL`, `SIGTERM` 전 시나리오 통과, 총 `63,931`건 커밋 트랜잭션 100% 복구, 복구 시간 `801ms~842ms`, 위반 `0`건).

## 4. `DURA-SOAK-1` 소크 테스트 (장시간 부하)

### 4.1. 무엇을 하는가
같은 서버를 24~72시간 계속 돌리며 부하를 걸고, 자원과 성능의 시간 추이에서 누수와 열화를 찾는다. 크래시가 아니라 "오래 돌면 서서히 망가지는" 결함이 대상이다.

### 4.2. 워크로드 (혼합)
- 주 부하: TPC-C 스타일 OLTP(쓰기 중심), 일정한 목표 TPS를 유지(최대 속도 아님).
- 보조: 읽기 전용 조회, 소량의 DDL, 연결 생성/종료 반복(풀 churn), 대형 결과셋 조회, 장시간 열린 트랜잭션 일부.
- 주기 이벤트: 시간당 1회 백업/복원 검증, 6시간마다 정상 재기동, 일정 간격으로 `kill -9` (킬 테스트와 결합).
- 연결 프로토콜: PGWire, TDS 병행.

### 4.3. 수집 지표 (1분 간격, `/metrics` + OS 지표)
| 지표 | 노리는 문제 |
| :--- | :--- |
| 프로세스 RSS, Go heap, 고루틴 수 | 메모리/고루틴 누수 (Rule 28) |
| 열린 파일 디스크립터 수 | 핸들 누수 (Rule 20) |
| 데이터/WAL/체크포인트 디렉토리 크기 | 정리(트렁케이트, 컴팩션) 실패 |
| TPS, 지연시간 p50/p99/p99.9 | 시간에 따른 성능 열화 |
| 오류율(롤백, 충돌, 타임아웃) | 서서히 증가하는 실패 |
| 커넥션 수, 락/충돌 카운터 | 풀 고갈, 락 잔류 |

### 4.4. 판정 기준 (자동)
- RSS/고루틴/FD는 워밍업(1시간) 이후 선형 증가 기울기가 임계 이하(예: 24시간 증가율 5% 이내).
- p99 지연이 시작 대비 2배를 넘지 않음. TPS 하락 10% 이내.
- 디스크 사용량은 데이터 증가량으로 설명 가능한 범위이며 WAL은 상한 유지.
- 종료 시 전체 정합성 검증(3.2의 D3 검사) 통과.
- 위반 시 마지막 정상 시점과 위반 시점의 pprof(heap, goroutine) 스냅샷을 자동 저장.

### 4.5. 구현 방향
- 위치: `cmd/soaktest/`와 `scripts/soak.sh`. 지표 수집 간격마다 CSV/JSON으로 저장하고 종료 시 요약 판정 리포트 생성.
- pprof 엔드포인트가 이미 있으면 재사용하고, 없으면 `--debug-addr` 옵션을 추가(기본 비활성).
- 처음에는 1시간 스모크 소크로 도구를 검증한 뒤 24시간, 72시간으로 확대.

### 4.6. 완료 기준
- 두 엔진 각각 72시간 무중단(예정된 재기동/킬 제외) 판정 기준 통과.

### 4.7. 1시간 스모크 소크 실측 결과 (2026-10-31, WiredTiger / PGWire)
- **실행 조건**: `bin/soaktest -duration 1h -sample 30s` (8 workers, 200 ops/s, 1,000 accounts)
- **정합성 검증**:
  - 잔액 총합 불변식: `SUM(balance) = 1,000,000` (PASS, 위반 0건)
  - 커밋 장부 대조: `acknowledged commits == soak_log rows (393,523 = 393,523)` (PASS)
  - 오류 및 직렬화 충돌: 총 `719,970` ops 중 처리되지 않은 오류 `0`건, 재시도 가능한 직렬화 충돌(`SQLSTATE 40001`) `3,016`건 정상 분리 (`DURA-SOAK-F1` 해결)
- **자원 및 지연 시간 추이**:
  - **열린 파일 디스크립터(`open_fds`)**: 1시간 내내 `28`개로 완전 고정 (`ratio = 1.00`, 핸들 누수 없음)
  - **지연 시간(`p99`)**: 초기 `5.78ms` ➔ 종료 `6.23ms` (`ratio = 1.08`, 성능 열화 없음)
  - **디스크 사용량**: `201MB` ➔ `216MB` (`soak_log` 39.3만 행 증가분 +15MB, 체크포인트 및 블록 재사용 정상)
  - **메모리(`rss_kb`) 추이 분석 (`DURA-SOAK-F2` 완료)**:
    - 200 ops/s 속도에서는 WiredTiger의 페이지 캐시(`cache_size=500M`)가 약 35분에 걸쳐 서서히 채워지며 프로세스 RSS가 `650MB~765MB`(WT 캐시 500MB + Go 런타임/CGo)에 도달한 뒤, 이후 WiredTiger eviction이 작동하여 59분 시점에는 `610MB`로 수렴함을 확인했다.
    - 초기(12~18분) 구간은 아직 500MB 캐시가 절반만 찬 상태(`335MB`)여서 단순 비율 비교(`late / early`)가 캐시 워밍업을 누수로 오판하는 문제가 있었으므로, `cmd/soaktest`에 `/metrics` 기반 Go 힙(`lionsql_memory_alloc_bytes`) 및 고루틴 수(`lionsql_goroutines`) 수집과 엔진 페이지 캐시 상한(`-rss-ceiling-mb 800`) 기준선을 반영했다.

## 5. `DURA-DOGFOOD-1` 개밥 먹기

자동화로 잡기 어려운 "실제 사용 패턴"을 위한 단계. 위험이 낮은 것부터 시작한다.

| 단계 | 내용 | 안전장치 |
| :---: | :--- | :--- |
| 1 | 개인용 Vaultwarden / Umami / Answer를 LionSQL로 운영 (연동 완료된 것부터) | 기존 DB를 주 DB로 두고 LionSQL은 섀도 운영, 결과 비교 |

## 7. 위험과 한계
- 통과해도 프로덕션 보증은 아니며, "알려진 데이터 유실 시나리오 없음"이라는 근거를 제공한다.
- 외부 요인(하드웨어 쓰기 캐시 거짓말, 파일시스템 버그)은 `SIGKILL` 테스트로 재현되지 않는다. 전원 차단은 별도 VM 레벨 테스트가 필요하며 본 계획 범위 밖(후속 검토).
- 소크 테스트는 시간이 오래 걸리므로 CI 상시 실행 대신 수동/야간 실행으로 운영한다.
