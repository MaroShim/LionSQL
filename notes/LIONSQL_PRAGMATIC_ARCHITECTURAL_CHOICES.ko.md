## 개요: LionSQL의 승리 공식

관계형 데이터베이스(RDBMS) 커널 개발에서 가장 빠지기 쉬운 함정은 **"대형 DBMS(Oracle, PostgreSQL, SQL Server)의 학술적이고 복잡한 메커니즘을 흉내 내는 것"**입니다. 복잡한 추상화 레이어, 거대 분산 조정자, 수천 줄의 AST 변환기는 10%의 특수한 경우를 해결하려다 시스템 전체를 불안정하게 만들고 유지보수 비용을 폭증시킵니다.

LionSQL을 관통하는 엔지니어링 철학은 극단적으로 명확합니다:

> **"복잡성을 늘려 10%를 개선하려 하지 않고, 낭비와 환상을 덜어내어 1,000%의 실질적 이득을 취한다 ([RULE:RadicalKISS])."**

본 문서는 상용 DBMS들이 관성적으로 답습해 온 복잡한 설계를 거부하고, 철저한 실용주의로 압도적인 성능과 안정성을 쟁취한 **"LionSQL의 9대 핵심 아키텍처 선택"**을 기록합니다.

## 근간 아키텍처 & 프로토콜: 시스템의 존립과 통합

### 1. 제로 사이드카 단일 정적 바이너리
* **버린 것**: PgBouncer(커넥션 풀러), Redis(캐시 계층), Nginx(리버스 프록시), ZooKeeper/etcd(분산 코디네이터) 등 분산 환경의 수많은 외부 데몬과 사이드카 종속성.
* **선택한 것**: 데이터베이스 코어 커널, PGWire(:5433)/TDS(:1433) 다중 와이어 리스너, REST API/임베디드 Web Studio(`embed.FS`), 고루틴 풀러, 크론 스케줄러를 **단 1개의 독립 정적 실행 파일(`bin/lionsql`)**로 번들링.
* **결과**: 외부 의존성 0, 배포 복잡도 0. `chmod +x && ./lionsql` 명령 하나로 0초 만에 상용 운영 환경이 즉시 가동됨.

### 2. 단일 카탈로그 프로세스 격리 & 가상 USE No-Op
* **버린 것**: 단일 프로세스 안에서 수십 개 데이터베이스를 복잡하게 멀티플렉싱하며 메모리 누수, 크로스 락 경합, 노이지 네이버를 유발하는 분산 카탈로그.
* **선택한 것**: 데이터 디렉터리(`--data-dir`)당 1개 카탈로그로 엄격히 물리 격리하고, 클라이언트의 `USE master`, `USE [SalesDB]` 등은 **TDS 환경 토큰만 맞춰주는 무해한 관용적 가상 No-Op(Tolerant Virtual No-Op)**으로 수용.
* **결과**: 복잡한 엔진 락킹 없이 서브마이크로초 격리 유지, 기존 SSMS/DBeaver 및 레거시 마이그레이션 스크립트 100% 호환.

### 3. PGWire 관문 + T-SQL 통합 엔진 (PL/pgSQL 중복 배제)
* **버린 것**: PostgreSQL 와이어 접속자를 위해 수천 줄짜리 별도의 PL/pgSQL 인터프리터를 중복 구현하고 유지보수하는 극심한 낭비.
* **선택한 것**: PGWire 포트(:5433)는 **순수한 네트워크 프로토콜 관문(Wire Gateway)**으로만 동작시키고, 내부 실행은 **모두 네이티브 T-SQL VDBE 엔진으로 단일화**.
* **결과**: 클라이언트는 세상에서 가장 대중적인 PostgreSQL 드라이버(`psql`, `pgx`, `lib/pq`, JDBC, Python psycopg)로 접속하면서도, Microsoft SQL Server의 강력한 T-SQL 제어문(`IF`, `WHILE`, `@변수`, `TRY...CATCH`, `sp_executesql`)을 그대로 실행하는 전무후무한 교차 호환성 달성.

### 4. 2-Tier 듀얼 파서 & 자동 폴백
* **버린 것**: 모든 SQL 쿼리를 무거운 ANTLR4 전체 문법 파서로 처리하려는 지연시간 낭비, 또는 정규식으로 때우다 중첩 괄호에서 터지는 취약점.
* **선택한 것**: 95%의 일반 DDL/DML/트랜잭션 쿼리는 제로-할당 **네이티브 프랫(Pratt) 파서**로 초고속 처리하고, Microsoft T-SQL 특수 구문(`WITH RECOMPILE`, `[dbo].[Proc]`)에 한해 **ANTLR4**로 자동 폴백.
* **결과**: 고빈도 OLTP 쿼리 파싱 지연시간 **0.5µs(서브마이크로초) 이하 달성**, 복잡한 엔터프라이즈 T-SQL 저장 프로시저 100% 문법 호환.

## 스토리지 & 메모리: 병목을 뚫어낸 고효율 경량화

### 5. 포인터 프리 플랫 레코드 (FlatRecord)
* **버린 것**: CPU를 25~50ns씩 갉아먹는 복잡한 비트 패킹/Varint 압축, 그리고 수많은 Go 포인터로 GC를 마비시키는 순수 슬라이스 구조(`performance` 모드).
* **선택한 것**: 포인터가 전혀 없는 **단일 연속 바이트 슬랩(FlatRecord) 레이아웃**.
* **결과**: 힙 메모리 **60.8% 절감**, Go GC 마크 페이즈 부하 제거로 32 동시 워커 TPC-C **TPS +46.4% 향상 (`3,722 TPS`)**, P99 지연시간 37.5% 단축.

### 6. WiredTiger 임시 테이블의 인메모리 바이패스
* **버린 것**: T-SQL 저장 프로시저에서 `#temp` 테이블이나 `@table_var`를 쓸 때마다 디스크 B+Tree 물리 파일(`.wt`)을 만들고 지우는 심각한 디스크 I/O 병목.
* **선택한 것**: WiredTiger 엔진 내부에 초경량 `memengine`을 심어, 임시 테이블 접두어(`#`, `@`, `__temp_`) 감지 시 **RAM으로 투명 라우팅**.
* **결과**: 임시 테이블 물리 디스크 I/O 0, 복잡한 배치 프로시저 처리 속도 수십 배 가속, 혼합 트랜잭션 롤백 완벽 보장.

## 실행기 & 옵티마이저: 상용 DB의 관성을 깬 하이브리드 실용주의

### 7. 2-Tier 하이브리드 실행기: VDBE VM(OLTP) + Volcano CBO(분석)
* **버린 것**: SQLite처럼 모든 복잡한 다중 조인까지 단일 바이트코드로 무리하게 욱여넣으려 하거나, 반대로 PostgreSQL처럼 단순 행 읽기까지 무거운 Volcano 반복자 트리로 순회하려는 단일 패러다임 도그마.
* **선택한 것**: 단순 CRUD와 프로시저 제어문은 **SQLite 스타일 VDBE 레지스터 VM(Tier 1)**으로 서브마이크로초 실행하고, 복잡한 다중 테이블 조인 및 비용 기반 최적화(CBO)는 **Volcano 엔진(Tier 2)**으로 분리.
* **결과**: 대부분의 상용/오픈소스 DB가 둘 중 하나만 선택해 병목을 겪는 것과 달리, **OLTP 초고속 응답성과 분석 조인의 확장성을 완벽히 양립**.

### 8. 상관 서브쿼리 유계 메모이제이션
* **버린 것**: 수백 줄의 취약한 AST 트리 재작성(Kim's Decorrelation)과 그로 인한 악명 높은 **Count Bug(`COUNT(*)=0`이 NULL로 왜곡)** 및 3VL 조인 왜곡 위험.
* **선택한 것**: 실행 계층에 단 40여 줄의 **4,096개 상한 격리 메모이제이션 캐시** 도입 (PostgreSQL 14 `Memoize`, MSSQL `Lazy Spool` 방식).
* **결과**: 500건 부서 집계 쿼리 **350ms ➔ 10.8ms (32배 단축)**, SQL 표준 시맨틱 왜곡 위험 0%, 난수/시간 함수(`NEWID`, `GETDATE`) 안전 바이패스.

## 클라이언트 생태계 호환성: 현실 도구를 정복한 묘수

### 9. TDS 영구 'Windows' 에뮬레이션
* **버린 것**: `runtime.GOOS`를 정직하게 검사해서 "macOS"나 "Linux"를 반환하려던 순진한 접근 (SSMS는 Windows SQL Server만 상정하여 작성되어 즉시 크래시 발생).
* **선택한 것**: OS에 관계없이 `sys.dm_os_host_info`와 TDS 환경 토큰에서 **무조건 `"Windows"`로 응답**.
* **결과**: 단 1줄의 고정 반환으로 SSMS Object Explorer, Azure Data Studio, DBeaver 등 전 세계 모든 관리 도구 100% 완벽 구동.

## 결론: "Less is More"의 데이터베이스 엔지니어링

LionSQL의 9대 아키텍처 선택은 기술적 화려함보다 **"운영 현장에서의 무중단 안정성, 초저지연 성능, 개발 생산성"**을 최우선으로 추구한 결과입니다. 

문제를 해결하기 위해 코드를 더하기보다, **불필요한 가정을 덜어내고 본질을 찌르는 설계**를 채택함으로써 LionSQL은 단일 바이너리 내에서 엔터프라이즈급 성능과 호환성을 모두 달성할 수 있었습니다.
