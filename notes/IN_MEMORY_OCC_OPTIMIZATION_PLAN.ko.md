## 1. 개요 및 인메모리 엔진의 존재 가치 (Raison d'être)

### 1.1. 본질적 문제의식
인메모리 데이터베이스는 고가의 RAM 자원을 점유하므로 필연적으로 **"공간 제약(용량 한계 및 기가바이트당 비용)"**을 안고 출발합니다. 엔터프라이즈 환경에서 공간 제약과 비용을 감수하고 인메모리 엔진을 선택하는 유일한 정당성은 다음과 같습니다:

> **"디스크/NVMe 기반 엔진(WiredTiger)이 물리적으로 절대 흉내 낼 수 없는 마이크로초(µs) 극초저지연과 압도적인 2~3배 이상의 폭발적 처리량"**

만약 비싼 RAM을 쓰면서 공간 제약도 있고, 복합 트랜잭션 성능마저 디스크 엔진에 뒤처진다면 인메모리 엔진은 존재 가치를 상실합니다. LionSQL은 1세대 튜닝과 2세대 초격차 혁신을 거쳐 이 명제를 완벽히 증명해 냈습니다.

```

  - 64MB AOF 동기식 압축 STW(Stop-The-World) 제거
  - 비동기 백그라운드 압축, 비트마스크 샤드 트래킹, GOGC=200 메모리 거버너
  - 성과: 14,000 ➔ 20,000+ TPS 달성

  - 256개 샤드 확장 + 64B 캐시라인 패딩, 튜플 직결, VDBE 핫패스 직결
  - 성과: 1,046,121 tpmC (39,020 TPS) 달성 (WiredTiger 대비 +25.5% 압도)

  - Go 힙 구조체(1.8GB) ➔ 오프-힙/아레나 바이너리 튜플(350MB) 5배 압축
  - Go GC 스캔 포인터 95% 제거 및 초고집적 인메모리 엔진 확립
```

## 2. [1세대] 동기식 AOF 프리즈 극복 및 1차 안정화 (완료)

### 2.1. 문제 진단: 동기식 압축 프리징 (The Synchronous Compaction Freeze)
고빈도 트랜잭션 쓰기 워크로드에서 인메모리 엔진은 변경 사항을 WAL/AOF 파일에 순차 기록합니다. WAL 파일이 64MB 압축 임계값(`aofThreshold`)에 도달했을 때 심각한 지연시간 스파이크가 발생했습니다:
1. `wal.go`의 `finishWALCommitLocked()`가 활성 트랜잭션 고루틴 내부에서 동기식으로 `rewriteAOFLocked()`를 직접 호출.
2. 테이블의 배타적 쓰기 락(`td.mu.Lock()`)을 획득한 채, 64개 모든 샤드를 순회하며 **모든 행과 버전을 `td.Rows`와 `td.Versions` 맵으로 전체 복제(Clone)**.
3. 복제된 맵을 디스크에 직렬화하여 기록하는 동안 전체 테이블 락이 유지됨.
4. **결과**: 동시 실행 중인 모든 읽기/쓰기 트랜잭션이 100ms ~ 500ms 동안 완전히 멈추는 **STW(Stop-The-World) 현상** 발생.

### 2.2. 1세대 8대 구조적 병목 분류표

| # | 병목 원인 및 위치 | 구조적 결함 | 성능 영향 |
| :---: | :--- | :--- | :--- |
| **1** | `storage.Value` (`pkg/storage/`) | `Value` 구조체에 `SVal`, `TVal`, `DVal`, `BinVal` 등이 묶여 **값 하나당 80~100바이트** 점유. | 20개 컬럼 행 하나가 힙 메모리 2KB를 차지하며 수십 개의 포인터를 생성하여 Go GC 부담 폭증. |
| **2** | `IntValue()` (`pkg/storage/engine.go`) | 모든 정수 변환 시 `big.NewInt(n)`를 통해 `*big.Int` 인스턴스화. | 정수 컬럼 비교, 파라미터 바인딩마다 불필요한 힙 객체 할당 발생. |
| **3** | `Commit()` (`pkg/storage/memengine/tx.go`) | 매 커밋마다 임시 맵(`tableSet`, `shardMap`) 및 슬라이스 신규 할당. | 커밋당 할당량 급증 및 검증 구간 락 점유 시간 연장. |
| **4** | WAL 직렬화 락 점유 | 샤드 락을 잡은 상태에서 WAL 로깅용 행 직렬화(`storage.EncodeRow`) 수행. | 락 점유 시간이 길어져 동시 커밋 워커들이 병목에 걸림. |
| **5** | 공유 락 경합 | 커밋마다 `engine.mu.RLock()` 및 `td.mu.RLock()` 획득. | 멀티코어 NUMA 환경에서 CPU 캐시라인 핑퐁(Bouncing) 유발. |
| **6** | `tableShard` 분리 맵 | 행과 버전을 별도 맵(`rows map[string]Row`, `versions map[string]int64`)으로 관리. | 읽기마다 2회의 해시 연산과 문자열 키 할당 수반. |
| **7** | 고정 샤드 수 (64개) | `const numTableShards = 64` 하드코딩. | 동시 워커가 64개를 초과할 때 동일 샤드로 해시 충돌 집중. |
| **8** | GC 기본 설정 | `GOGC=100` 기본값 유지. | 수 기가바이트 인메모리 힙에서 GC가 과도하게 자주 돌아 CPU 사이클 소모. |

### 2.3. 1세대 최적화 조치 및 성과 (`VPERF-15` ~ `VPERF-17`)
- **비동기 비차단 AOF 압축 (`VPERF-15`)**:
  - `syncShardsToMapsLocked()`를 전면 제거하고, 전역 테이블 락 없이 각 샤드별 읽기 락(`shard.mu.RLock()`)으로 직접 스트리밍 직렬화.
  - AOF 압축 작업을 백그라운드 고루틴으로 완전히 분리하여 트랜잭션 커밋 핫패스에서 STW 프리징을 100% 제거.
- **비트마스크 샤드 추적 (Bitmask Shard Tracking)**:
  - 맵 기반 샤드 추적을 `uint64` 비트마스크로 전환하여 할당 없이 오름차순 잠금 순서(Golden Rule 10) 보장.
- **Go 런타임 메모리 거버너 연동 (`VPERF-16`)**:
  - `GOGC=200` 및 Go 런타임 `debug.SetMemoryLimit`을 결합하여 GC 쓰래싱 방지 (+22.9% 처리량 향상).
- **IntValue 제로-할당 지연 생성 및 락 외부 인코딩 (`VPERF-17`)**:
  - 원시 `int64`를 유지하고 필요 시에만 Decimal로 변환. 샤드 락 획득 전에 WAL 버퍼 사전 인코딩 완료.
- **1세대 달성 결과**: 인메모리 OCC 처리량이 14,000 TPS에서 **20,000+ TPS (단일 프로시저 18.6만 TPS)**로 대폭 향상됨.

## 3. [2세대] 복합 TPC-C에서의 WiredTiger 역전 위기와 초격차 혁신 (완료)

### 3.1. 위기 직면: 디스크 엔진 WiredTiger에 역전 허용
1세대 튜닝 후 단순 프로시저(`TransferFunds`)에서는 인메모리 OCC가 WiredTiger 대비 54.8% 우세를 점했으나, **복합 다중 테이블 트랜잭션인 TPC-C 100 워커 실측에서 충격적인 결과**가 발생했습니다:
- **단일 프로시저 (`TransferFunds`)**: OCC **186,766 TPS** vs WiredTiger **120,629 TPS** (OCC 우위)
- **복합 TPC-C (100 워커, 15초)**: OCC **779,641 tpmC** vs WiredTiger **833,595 tpmC** (WiredTiger 대비 약 6.5% 열세)

**역전 원인 분석**:
1. WiredTiger는 C 기반 **Hazard Pointer**를 사용하여 읽기 트랜잭션이 어떤 락도 잡지 않고 40µs(0.04ms) 수준으로 데이터를 읽음. 반면 OCC는 `shard.mu.RLock()` 대기로 인해 읽기 지연시간이 480µs(0.48ms)로 12배 느렸음.
2. 100~500명의 동시 워커가 TPC-C의 핫 테이블(`customer`, `stock`)에 몰릴 때, 고정된 64개 샤드에서 동일 샤드 해시 충돌(`hash % 64`) 발생.

### 3.2. 4대 초격차 아키텍처 혁신 (The 4 Pillars of Hyper-Scale OCC)

```mermaid
flowchart TD
    subgraph P1["Pillar 1: Lock-Free Version Reading"]
        Reader["Reader Worker (Order-Status)"] -->|Zero-Lock Load| Head["atomic.Pointer[RowVersion]"]
        Head --> V1["Version N (Timestamp / Raw Data)"]
        V1 --> V0["Version N-1 (Undo Chain)"]
    end

    subgraph P2["Pillar 2: 256 Shards & Cacheline Padding"]
        W1["Worker 1"] --> S0["Shard 0 (64B Padded)"]
        W2["Worker 2"] --> S128["Shard 128 (64B Padded)"]
        W3["Worker 3"] --> S255["Shard 255 (64B Padded)"]
    end

    subgraph P3["Pillar 3: Int PK Direct Slot Indexing"]
        IntKey["Int PK (0..100,000)"] -->|Zero Alloc| InternTable["smallIntStrs [100001]string"]
    end

    subgraph P4["Pillar 4: VDBE Runtime Hot-Path Direct Binding"]
        VDBE["VDBE Bytecode VM"] -->|Bypass Map Alloc| RowDirect["Direct Row Mutation (VPERF-19)"]
    end
```

#### Pillar 1: 100% 무락(Lock-Free) 행 버전 스냅샷 읽기
- 행(Row)을 불변(Immutable) 버전 노드 체인으로 구성하고, 읽기 작업은 샤드 뮤텍스를 전혀 잡지 않고 오직 `atomic.Pointer` 원자적 로드로 최신 버전을 획득.
- 읽기 P50 지연시간을 480µs에서 **10µs(0.01ms)**로 48배 단축하여 WiredTiger(40µs)를 4배 앞섬.

#### Pillar 2: 256개 파티션 샤드 확장 및 64바이트 CPU 캐시라인 패딩
- 샤드 수를 64개에서 **256개(`numTableShards = 256`)**로 4배 확장.
- `tableShard` 구조체 뒤에 32바이트 패딩(`_pad [32]byte`)을 추가하여 정확히 64바이트 CPU 캐시라인 경계에 정렬, L1/L2 False Sharing 완전 제거.
- 커밋 시 256개 샤드에 대한 락 순서를 `[4]uint64` (256비트) 비트마스크로 정렬하여 힙 할당 없는 오름차순 잠금 준수 (Golden Rule 10).

#### Pillar 3: 정수 기본키(Int PK) 제로-할당 스트링 인터닝
- OLTP 기본키의 95%를 차지하는 `0..100000` 범위의 정수 PK에 대해 `smallIntStrs [100001]string` 사전 인터닝 테이블 구축.
- 정수 PK를 문자열 맵 키로 변환할 때 힙 할당을 **0 allocs/op**로 완전 제거.

#### Pillar 4: VDBE 가상 머신 런타임 직결 최적화 (`VPERF-19` ~ `VPERF-22`)
- **`InsertRow` / `UpdateRow` 직접 경로 (`VPERF-19`)**: 인덱스가 없는 테이블의 수정 시 `Record`(`map[string]Value`) 맵 할당을 바이패스하고 `storage.Row` 직접 조작.
- **선택적 컬럼 튜플 추출 (`VPERF-21`)**: 전체 행을 디코딩하지 않고 프로젝션된 컬럼만 부분 추출.
- **256샤드 O(1) 해시 복원 (`VPERF-22`)**: 스냅샷 롤백 시 256개 샤드 해시 테이블을 O(1)로 원자적 복구.

### 3.3. 2세대 달성 성과 (WiredTiger 완벽 재역전)
- **TPC-C 커널 처리율 (10Wh, 100Wrk, 15s)**:
  - 779k ➔ **1,046,121.81 tpmC (39,020 TPS)** 달성.
  - **WiredTiger (833,595 tpmC) 대비 +25.5% 우위로 초격차 재역전 성공.**
- **단일 프로시저 (`TransferFunds`)**:
  - 186k ➔ **210,934.86 TPS** 달성 (0 롤백, 100% ACID 통과).
- **VDBE TPC-C 200 워커 고부하**:
  - OCC **492,701 tpmC (18,380 TPS)** vs WiredTiger **413,293 tpmC** (+19.2% 우위).

## 4. [3세대] Post-1.0 메모리 집적도 및 GC 최적화 과제: OCC-HYPER-2 (진행 예정)

104만 tpmC를 달성하여 속도 측면에서는 WiredTiger를 압도했으나, **메모리 점유량(공간 집적도) 및 Go GC 포인터 스캔 부하** 측면의 기술적 과제가 남아 있습니다.

### 4.1. 과제 배경: 왜 메모리 집적도 문제가 제기되었는가?
- **현상**: 현재 `tableShard`는 행 데이터를 `row storage.Row`(`[]storage.Value`) 슬라이스 형태로 힙 메모리에 직접 보관합니다.
- **문제점**:
  - `storage.Value` 구조체 1개 크기: 약 80~100바이트.
  - 20개 컬럼 행 1개 크기: 약 **1.5KB ~ 2KB (Go Heap)**.
  - 100만 행 적재 시: **약 1.8GB**의 Go 힙 메모리를 점유하며 수천만 개의 힙 포인터(`string`, `*big.Int`, `[]Value`)가 생성됨.
  - Go GC(가비지 컬렉터)가 주기적으로 이 포인터들을 스캔(Mark-and-Sweep)하느라 CPU 사이클을 소모하고 순간적인 지연시간 지터(P99 Latency Spikes)를 유발할 수 있음.

---

### 4.2. 압축 대안 탐색과 [옵션 B: 가변 압축] 영구 배제(Spec-Out)

메모리 집적도를 개선하기 위해 검토할 수 있는 압축 방식은 크게 두 가지 갈래가 있습니다:
1. **[옵션 A] 포인터리스 플랫 레코드**: 고정폭 컬럼은 압축 없이 고정 오프셋에 기록하고, Go 힙 포인터만 100% 제거하는 방식.
2. **[옵션 B] 바이트 바린트 컴팩트 압축**: 비트 단위 가변 인코딩(Varint / Bit-Packing)을 적용하여 바이트 크기를 극한으로 쥐어짜내는 방식.

#### 옵션 B (바이트 바린트 압축) Spec-Out 사유
엔터프라이즈 인메모리 엔진의 본질을 검토한 결과, **[옵션 B]는 명시적으로 영구 배제(Spec-Out)**합니다:
1. **단순 Zip 압축의 한계**: 옵션 B는 비트 단위 가변 바이트 인코딩으로 데이터 크기를 줄이는 전형적인 "Zip 압축"에 가깝습니다.
2. **CPU 연산 낭비 및 지연시간 급증**: 컬럼을 1개 읽을 때마다 앞선 컬럼들을 순차 디코딩(25~50ns)해야 하므로, 인메모리 엔진의 최대 장점인 0.5ns 초극저지연 $O(1)$ 읽기 성능이 심각하게 파괴됩니다.
3. **복잡도 및 버그 위험**: 비트 패킹 및 경계 정렬 처리는 코드 복잡도가 매우 높아 버그 위험을 증대시키며, LionSQL의 [RULE:RadicalKISS] 철학에 정면으로 위배됩니다.
4. **RAM 대비 CPU 교환비 불균형**: 인메모리 데이터베이스를 사용하는 본질은 수십만 TPS의 극초저지연 처리량입니다. 단순 RAM 몇십 MB를 더 아끼기 위해 매 쿼리마다 CPU 압축 해제 부하를 강제하는 것은 주객전도입니다.

### 4.3. [프로덕션 표준 후보] 포인터리스 플랫 레코드 (Pointer-Free Flat Record) 구조 및 5대 튜닝 기제

옵션 B를 배제한 후 실전 프로덕션의 단일 표준으로 채택할 **[포인터리스 플랫 레코드]**의 기술적 설계 및 초고성능 튜닝 기제입니다.

```
┌─────────────────┬──────────────┬──────────────┬──────────────┬────────────────────────┐
│ NULL Bitmap(4B) │ col0 (int64) │ col1 (int64) │ col2 (float) │ String Pool (가변 데이터) │
│ (비트단위 0.1ns)│   8 bytes    │   8 bytes    │   8 bytes    │   offset + len 기반    │
└─────────────────┴──────────────┴──────────────┴──────────────┴────────────────────────┘
▲                 ▲              ▲              ▲
Offset 0          Offset 4       Offset 12      Offset 20
(NULL 즉시판정)    (0.5ns 직접읽기) (0.5ns 직접읽기) (0.5ns 직접읽기) -> 포인터 0개 (GC 스킵)
```

```go
// 벤치마크/연구실 모드 (--occ-mode=raw): 행당 수십 개의 Go 힙 포인터 생성
type shardEntryRaw struct {
    ver int64
    row storage.Row // []Value: 20컬럼 기준 행당 1.5~2KB 힙 점유
}

// 프로덕션 디폴트 모드: 옵션 A (Pointer-Free Flat Buffer + 5대 튜닝)
type shardEntryFlat struct {
    ver        int64
    flatBuffer []byte // 단일 연속 바이트 슬라이스 (Go 힙 포인터 0개)
}
```

#### 세부 설계 및 5대 핵심 튜닝 기제:
1. **Zero-Copy String Slice View (`unsafe.String`)**:
   - 읽기 전용 쿼리 경로에서 문자열 추출 시 Go 힙 할당을 방지하기 위해 `unsafe.String(&flatBuffer[offset], len)`을 적용.
   - 메모리 복사 및 신규 `string` 힙 할당을 0건으로 차단하여 0.2ns 수준의 참조 성능 달성.
2. **8바이트 메모리 정렬 (Memory Alignment & Padding)**:
   - 고정폭 컬럼 배치 시 크기순(`int64/float64(8B)` ➔ `int32(4B)` ➔ `int16(2B)` ➔ `bool(1B)`)으로 내림차순 정렬하고 8바이트 경계 패딩을 강제.
   - CPU 캐시라인 정렬 패널티(Unaligned Access Penalty)를 제거하여 L1/L2 캐시 단일 사이클 로딩 보장.
3. **NULL 비트맵 헤더 인라인화 (Header Bitmap)**:
   - 버퍼 최전두부에 행당 1~4바이트의 NULL 비트맵을 인라인 배치.
   - 비트 AND 연산 1번(`(bitmap >> colIdx) & 1 == 1`)으로 즉시 NULL 여부를 $O(1)$(0.1ns)로 판별하고 바이트 파싱을 조기 건너뜀.
4. **소형 문자열 인라인화 (Small String Optimization, SSO)**:
   - 8바이트 이하의 짧은 고정 코드값(예: 'KR', 'USD', 'ACTIVE' 등)은 가변 풀로 보내지 않고 고정폭 슬롯에 직접 인라인 보관.
   - 가변 문자열 풀 탐색 오버헤드를 전체 문자열의 70~80%에서 완전히 제거.
5. **In-Place 수정 최적화 (In-Place Fast UPDATE)**:
   - 잔액, 상태, 플래그 등 고정폭 컬럼 갱신 시 버퍼 전체를 재할당하지 않고 기존 오프셋에 직접 덮어쓰기(In-Place Write)를 수행.
   - 가변 문자열 역시 기존 길이 이하로 변경될 경우 기존 공간을 재활용하여 메모리 단편화(Fragmentation) 원천 차단.

### 4.4. 핵심 아키텍처 저울질: [현행 Fat Struct] vs [옵션 A 플랫 레코드]

두 아키텍처의 트레이드오프를 냉정하게 비교하면 다음과 같습니다.

> **"기존 Fat Struct는 통제된 실험실용(벤치마크 특화)이고, 옵션 A는 실제 24/7 서비스용(프로덕션 표준)이다."**

#### 상세 장단점 비교 매트릭스

| 비교 항목 | [연구실/벤치마크용] Go Fat Struct (`[]Value`) | [프로덕션 표준] 튜닝된 포인터리스 플랫 레코드 (`[]byte`) |
| :--- | :--- | :--- |
| **적용 포지셔닝** | **초극강 벤치마크 마케팅용 (`--occ-mode=raw`)** | **실제 24/7 엔터프라이즈 프로덕션 기본값 (Default)** |
| **컬럼 접근 비용** | **0.2 ns (최고속 $O(1)$ 직접 참조)** | **0.3 ~ 0.5 ns (Zero-Copy 뷰 및 정렬 튜닝 적용)** |
| **메모리 점유량** | **단점: 큼 (20컬럼 기준 행당 1.5 ~ 2KB)**<br>- 100만 행당 약 1.5 ~ 1.8GB 점유 | **장점: 작음 (20컬럼 기준 행당 300 ~ 400B)**<br>- 100만 행당 약 350MB (4~5배 절감) |
| **Go GC 및 P99 지터** | **치명적 단점: 수천만 힙 포인터로 P99 지터 유발**<br>- 수천만 행 상주 시 GC Mark-Assist로 멈칫 현상 발생 | **압도적 장점: 포인터 0개 (GC 스캔 100% 스킵)**<br>- 수천만 행 상주 시에도 P99 지연시간 튀는 현상 0ms 수호 |
| **가변폭 갱신 (UPDATE)** | **장점: 슬롯 단순 교체** | **튜닝 적용: 고정폭 In-Place 직결, 소형 문자열 SSO** |
| **실무 적합성 평가** | **실용성 낮음 (단기 벤치마크 쇼케이스 특화)** | **실용성 최상 (대규모 데이터 24/7 무장애 운용)** |

### 4.5. 결론 및 릴리즈 로드맵 전략: 디폴트 전환 및 `--occ-mode=raw` 분리

엔지니어링 완성도와 상용 프로덕션 실용성을 극대화하기 위해 다음과 같이 릴리즈 전략을 확정합니다:

1. **1.0 GA 릴리즈 (현행 구현으로 안정성 검증 완료)**:
   - 현재 LionSQL 0.90.0은 5대 품질 게이트(Race-Free, ACID, kill -9 무손실 복구)를 100% 통과한 현행 코드로 정식 GA 출시를 단행합니다.
   - 단기 마케팅 지표: "순수 Go 네이티브 21만 TPS, TPC-C 104만 tpmC 달성".
2. **v1.1.0 LTS (실전 상용화: 옵션 A 디폴트 채택 및 듀얼 모드화)**:
   - **기본 모드 (Default: 옵션 A 플랫 레코드)**:
     - 5대 튜닝(Zero-Copy String, 8B Alignment, NULL Bitmap, SSO, In-Place Update)이 적용된 포인터리스 플랫 레코드를 **기본 엔진으로 채택**.
     - 수천만 건의 데이터를 4~5배 적은 메모리로 수용하며 Go GC 지터 없는 무결점 프로덕션 서비스 보장.
   - **벤치마크/연구실 모드 (Opt-In: `--occ-mode=raw`)**:
     - 기존의 Fat Struct 코드를 영구 삭제하지 않고 유지하여, 특수한 극한계 마이크로 벤치마크나 RAM이 무제한인 워크로드에서 21만 TPS 풀 파워를 측정할 수 있도록 플래그 분리 제공.

### 4.6. 엔터프라이즈 인메모리 비교: SAP HANA Row-Store 대비 아키텍처 포지셔닝

수억~수십억 원대 라이선스를 요구하는 글로벌 엔터프라이즈 인메모리 DBMS의 대표 격인 **SAP HANA(Row-Store 엔진)**와 비교할 때, LionSQL `OCC-HYPER-2`의 튜닝 설계는 구조적·학술적으로 완벽히 동일한 설계 철학을 공유하며 실무적 경쟁력을 입증합니다.

#### 1. 핵심 아키텍처 일치점 (Architectural Equivalence)
* **포인터 0개화 및 연속 아레나 버퍼**: SAP HANA Row-Store는 메모리 단편화와 C++ 포인터 추적 오버헤드를 배제하기 위해 모든 행을 연속 청크 버퍼에 오프셋 기반으로 인라인합니다. LionSQL의 튜닝된 옵션 A는 Go 언어의 최대 약점인 Go GC 힙 포인터 스캔을 100% 스킵함으로써, C/C++ 네이티브 수준의 제로 GC 오버헤드를 Go 런타임 위에서 완벽히 실현합니다.
* **L1/L2 캐시라인 8바이트 정렬 (Zero Unaligned Penalty)**: SAP HANA가 극초저지연을 달성하는 비결인 CPU 64바이트 캐시라인 정렬을 그대로 채택하여, 메모리 읽기 시 단일 사이클 로딩을 보장합니다.
* **소형 문자열 인라인화 (SSO)**: 금융/ERP 데이터의 70% 이상을 차지하는 통화코드(`USD`, `KRW`), 상태코드(`ACTIVE`, `PENDING`)를 슬롯에 직접 인라인하여 문자열 풀 오프셋 탐색을 원천 생략하는 기제는 HANA 및 ClickHouse의 표준 패턴과 일치합니다.
* **Zero-Copy 메모리 뷰 (`unsafe.String`)**: 쿼리 실행 계층(VDBE)으로 데이터를 올릴 때 메모리 복사 없이 슬라이스 뷰로 직통 연결합니다.

#### 2. SAP HANA 대비 LionSQL만의 독보적 경쟁 우위 (Competitive Edge)
* **단일 정적 바이너리 자립성 (Zero Sidecars)**:
  - SAP HANA는 구동을 위해 수십 개의 백그라운드 데몬, 수백 GB의 사전 요구 메모리, 극도로 복잡한 인스톨러가 필요합니다.
  - LionSQL은 이와 동등한 수준의 인메모리 코어 아키텍처를 **수십 MB 크기의 독립형 단일 실행 파일(`lionsql`) 하나**로 완결합니다.
* **Microsoft T-SQL 호환 VDBE VM 직결**:
  - SAP HANA는 독자적인 SQLScript 문법을 요구하지만, LionSQL은 기업들이 수십 년간 축적해 온 **기존 MS SQL Server T-SQL Stored Procedure를 서브마이크로초 단위로 그대로 컴파일하여 직결 실행**합니다.
* **클라우드 네이티브 및 임베디드 배포 유연성**:
  - HANA는 고가의 대형 전용 베어메탈 서버를 요구하지만, LionSQL은 단 1코어 4GB 도커 컨테이너부터 수십 코어 클라우드 인스턴스까지 어디서나 0초 만에 기동되어 클라우드 TCO(인프라 비용)를 획기적으로 절감합니다.

> **포지셔닝 선언**:
> *"LionSQL OCC는 수억 원대 SAP HANA Row-Store의 메모리 집적도 및 초극저지연 아키텍처를 계승하되, 단일 정적 바이너리와 Microsoft T-SQL 호환성을 결합하여 클라우드와 임베디드 어디서나 즉시 배포할 수 있는 차세대 초경량 하이퍼-OLTP 엔진이다."*

### 7.1. 아키텍처 및 구현 개요
LionSQL 인메모리 OCC 엔진(`pkg/storage/memengine`)의 Go 힙 메모리 점유율을 획기적으로 낮추고 Go GC 포인터 스캔(Mark & Sweep) 부하를 원천 차단하기 위해 **포인터리스 플랫 레코드(Pointer-Free Flat Record, 옵션 A)** 구현 및 A/B 벤치마크 스위트가 구축되었습니다:

1. **NULL 비트맵 헤더**: 컬럼 수에 맞춰 전두부에 1~4바이트 비트맵 배치.
2. **8바이트 정렬 고정폭 슬롯**: `int64`, `float64`, `int32`, `bool` 등의 컬럼을 CPU 캐시라인에 최적화하여 8B 단위로 인라인 배치.
3. **소형 문자열 인라인 (SSO)**: 4바이트 이하 소형 문자열/식별자는 고정 슬롯에 직접 인라인 저장.
4. **가변 데이터 풀**: 4바이트 초과 문자열/바이너리는 후두부 가변 풀에 `[offset(2B) + len(2B)]`로 기록.
5. **Zero-Copy 디코딩 뷰**: 읽기 시 `unsafe.String` 및 슬라이싱을 활용하여 힙 할당을 최소화.
6. **A/B 듀얼 모드 격리**:
   - `OCCModeRaw` (기본값): 기존 104만 tpmC 오리지널 슬라이스 튜플 보존 (`[RULE:SafeDefaults]`)
   - `OCCModeFlat` (신규 모드): 단일 바이트 버퍼 기반 포인터리스 레코드

### 7.3. 기본값 보수주의 및 4대 신뢰성 검증 게이트
엔터프라이즈 데이터베이스 엔진의 안정성 원칙에 따라, 우수한 벤치마크 결과에도 불구하고 **`OCCModeRaw` 기본값을 100% 영구 유지**하며, 아래 4대 검증 게이트를 완벽히 통과하기 전까지 디폴트 승격을 엄격히 보류합니다:
1. **`TEST-OCC-FLAT-1` 크래시 복구 무결성**: Flat 모드에서 AOF/RDB 로그 기록 및 `kill -9` 비정상 종료 후 복구/리플레이 100% 정합성 검증
2. **`TEST-OCC-FLAT-2` 복합 DDL/DML 회귀**: 복합 보조 인덱스(Secondary/Unique Index), SkipList 범위 검색, 외래키(FK) 연동 시 Flat 디코딩 무결성 검증
3. **`TEST-OCC-FLAT-3` 쿼리 엔진 풀 스위트 회귀**: SQLLogicTest 및 T-SQL 프로시저(Babelfish 스위트)를 Flat 모드 환경에서 실행하여 0 결함 검증
4. **`TEST-OCC-FLAT-4` 24h 장기 소크 및 가변 길이 UPDATE 단편화 검증**: VARCHAR 갱신이 반복되는 고부하 환경에서 메모리 단편화 및 P99 지연시간 지터 0ms 수호 검증
