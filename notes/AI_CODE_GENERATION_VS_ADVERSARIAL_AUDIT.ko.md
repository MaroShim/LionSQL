## 1. 시작하며: 현장에서 터져 나온 솔직한 탄식

LionSQL 1.0 정식 릴리스를 앞두고 197건의 잠재 결함 중 치명적인 **P0 결함(Must Fix 30선)**을 TDD(Test-Driven Development)로 하나씩 치료해 나가던 중, 다음과 같은 코드를 마주했을 때 엔지니어는 깊은 한숨과 함께 근본적인 의문을 던지게 되었습니다:

1. **`P0-01`**: 8바이트 슬롯에 태그 바이트(`slot[1] = 0x00`)를 쓰자마자 바로 다음 줄에서 가변 힙 오프셋(`PutUint32(slot[0:4], vOff)`)을 덮어써서, 오프셋이 커지는 순간 인라인 데이터로 오인해 테이블을 영구 오염시키던 코드.
2. **`P0-02`**: 메모리 절감을 위해 행 데이터를 플랫 버퍼에 압축해 두고는, 디스크 스냅샷 동기화 시에는 정작 빈 포인터 껍데기(`entry.row`)만 복사해 넘겨 디스크에 빈 테이블을 저장하던 코드.
3. **`P0-03`**: WAL 재생 시 디스크 읽기 일시 오류(`syscall.EIO`)가 발생하자 이를 크래시 테일 잘림으로 오인하여, 뒤에 멀쩡히 살아있는 수만 건의 정상 커밋 트랜잭션을 디스크에서 `file.Truncate()`로 영구 삭제하고는 성공(`nil`)으로 부팅하던 코드.
4. **`P0-04`**: `ALTER TABLE ADD COLUMN`을 실행하자 기존 플랫 버퍼를 뜯어보지도 않고 버려버린 채, 비어있던 슬라이스에 새 컬럼 1개만 달랑 붙여 기존의 모든 컬럼 데이터를 전량 소멸시키던 코드.
5. **`P0-05`**: 구조체에 `partMu sync.RWMutex`를 선언해 두고는, 트랜잭션 커밋(`tx.go`)은 `partMu`를 잡고 쓰고, 조회(`ddl.go:GetPartitions`)는 엉뚱한 `td.mu`를 잡고 읽어 동시 실행 시 즉시 크래시를 유발하던 락 엇박자 코드.

이 황당한 코드들을 눈으로 직접 확인한 엔지니어는 자연스럽게 두 가지 질문을 던질 수밖에 없었습니다:

> *"일관성도 없고 엉망진창인데, 신기한 거는 지금 이 프로젝트 전체가 이런 방식으로 쌓아올려졌는데 어떻게 지금까지 멀쩡히 동작하고 있었지?"*
> 
> *"그런데 코드를 짤 때는 이렇게 naive했던 AI가, 감사를 할 때는 도대체 이런 문제들을 어떻게 귀신같이 찾아내는 거지?"*

본 문서는 자율형 AI 에이전트와 인간 엔지니어가 협업하여 단일 바이너리 OLTP 데이터베이스 엔진을 구축하는 과정에서 목격한 **AI 코드 생성의 맹점(The Illusion of Working Code)**과 **적대적 전수 감사의 작동 원리(Adversarial Cross-Referencing)**를 솔직하고 체계적으로 기록한 엔지니어링 회고록입니다.

## 2. '엉망진창'인데 어떻게 지금까지 돌아가고 있었을까?

겉보기에는 수십만 건의 쿼리를 문제없이 처리하고, 수백 개의 기존 단위 테스트를 100% 통과하고 있었던 시스템 아래에 어떻게 이런 치명적인 시한폭탄들이 숨어있을 수 있었을까요?

### 2.1 단일 스레드 '행복 경로(Happy Path)'라는 거대한 착시
기존의 단위 테스트들은 대부분 순차적으로 작성되었습니다:
- *"테이블을 만든다 ➔ 데이터를 넣는다 ➔ 조회한다 ➔ 값이 일치한다 ➔ PASS."*
- 단 하나의 고루틴이 정해진 순서대로 실행했기 때문에, 락을 엉뚱한 것을 잡았든 아예 안 잡았든 물리적으로 메모리 충돌(Race)이 발생할 수 없었습니다.
- 시스템의 '행복 경로(정상적인 순차 흐름)'만 검증하는 테스트 스위트는, 그 뒤에 숨어있는 수많은 동시성 지뢰를 완벽하게 은폐하는 거대한 착시를 만들어냅니다.

### 2.2 Go 런타임의 '확률적 충돌(Probabilistic Race Timing)'
Go 언어의 내장 맵(`map`)은 동시 읽기/쓰기를 감지하면 프로세스를 즉각 패닉(`fatal error: concurrent map read and map write`)으로 종료시킵니다. 하지만 이 감지는 **두 고루틴이 물리적으로 정확히 같은 수십 나노초 이내에 동일한 메모리 버킷을 건드릴 때만** 발생합니다.
- 로컬 개발 환경이나 가벼운 단기 테스트에서는 두 요청이 1마이크로초씩 비껴가면서 우연히 충돌을 피합니다.
- 그러나 실제 프로덕션 환경에 배포되어 동시 접속자 수십 명이 몰리고, 백그라운드 모니터링이 1초마다 통계를 폴링하는 순간, 이 확률적 회피는 깨어지고 서버는 불특정 시점에 의문사하게 됩니다.

### 2.3 국소적 기능 추가 중심(Feature Velocity)의 누적 부채
AI 에이전트에게 기능을 요청할 때, 프롬프트는 보통 국소적입니다:
- *"파티셔닝 기능을 구현해줘"*, *"AOF 재작성 기능을 추가해줘"*, *"FlatRecord 최적화를 적용해줘"*.
- AI는 주어진 목표 기능의 단위 테스트를 통과시키는 데 모든 집중력을 쏟아붓습니다. 
- 그 결과, `tx.go`를 작성할 때는 파티션 락을 신경 썼지만, 나중에 `ddl.go`나 `persistence.go`를 작성할 때는 과거의 컨텍스트를 잊어버리고 엉뚱한 락을 쓰거나 아예 락을 빼먹는 **도메인 간 교차 영역의 엇박자**가 구조적으로 누적됩니다.

## 3. 코드를 짤 때는 바보인데 감사는 왜 귀신같이 할까?

그렇다면 가장 큰 의문이 남습니다. **코드를 생성할 때는 이렇게 근시안적이고 naive했던 AI가, 감사를 수행할 때는 어떻게 사람이 수개월 동안 찾지 못할 미세한 동시성 지뢰와 락 누락을 핀셋으로 집어낼 수 있었을까요?**

이 현상은 AI 모델의 **'코드 생성 모드(Generation Mode)'**와 **'적대적 감사 모드(Adversarial Audit Mode)'** 사이의 근본적인 인지 및 연산 메커니즘 차이에서 기인합니다.

### 3.1 생성 모드: '앞만 보고 달리는 말' (Forward Token Prediction)
- 코드를 짤 때의 AI는 **"이 함수를 완성하여 컴파일이 되게 하고, 주어진 요구사항의 결과값을 내놓아야 한다"**는 목표(Happy Path)를 향해 직진합니다.
- 슬라이스에 `append`를 하고, 맵에 값을 넣고, 타입을 맞추는 등 "동작하는 형태의 코드 블록"을 완성하는 데 어텐션(Attention) 자원이 고도로 집중됩니다.
- 이 과정에서 *"혹시 다른 고루틴이 동시에 이 슬라이스를 읽고 있으면 어쩌지?"*, *"혹시 AOF 복구 경로에서 이 함수를 부르면 락이 깨지지 않을까?"* 같은 시스템적 부작용(Side Effects)은 어텐션 윈도우의 중심에서 밀려납니다.

### 3.2 감사 모드: '전체 판을 훑는 적대적 공격자' (Adversarial Invariant Scan)
반면, 이번 197건 전수 감사에서 AI에게 부여된 역할은 코드를 작성하는 것이 아니라 **"시스템을 파괴할 수 있는 모든 틈새를 찾아내는 적대적 공격자(Attacker)"**였습니다:
- *"너는 시스템을 다운시키려는 악랄한 QA 엔지니어다. 전 소스코드를 전수 스캔하여 락 누락, 데이터 오염, 무음 에러 무시를 색출하라."*
- 이때 AI의 사고방식은 180도 뒤집힙니다. 어떻게 코드를 완성할까를 고민하는 것이 아니라, **"어디를 찌르면 서버가 크래시 날까?"**에만 집중합니다.

### 3.3 인간의 뇌 vs AI의 기계적 교차 대조(Cross-Referencing)
인간 엔지니어는 3만~5만 줄의 대형 코드베이스를 리뷰할 때 필연적으로 인지적 피로와 기억 편향을 겪습니다:
- *"아, 아까 `tx.go` 보니까 파티션 락 잘 걸어놨던데. `ddl.go`도 당연히 잘 걸려 있겠지."* (인간 뇌의 자동 완성 착시)
- 하지만 AI는 피로를 느끼지 않는 기계적 인덱서입니다.
  1. `TableData` 구조체에 `Partitions map`과 `partMu`가 선언되어 있음을 인지하면,
  2. 코드베이스 전체에서 `Partitions`라는 단어가 사용된 **28개 호출 위치(Call sites)를 0.1초 만에 전수 추출**합니다.
  3. 그리고 각 호출 위치의 앞뒤 5줄을 정밀 대조하여, `partMu.Lock()` 또는 `partMu.RLock()`이 없는 구멍을 수학적으로 찾아냅니다.
  4. ➔ *"호출 위치 1(`tx.go`)은 `td.partMu`를 쓰는데, 호출 위치 2(`ddl.go:542`)는 엉뚱하게 `td.mu`를 읽고 있다. 서로 다른 락으로 인한 Data Race 확정!"*

인간이 며칠 밤을 새워도 놓치기 쉬운 **'전체 코드베이스 대상 정적 전수 교차 대조'**를 AI는 단 수 초 만에 오차 없이 수행해 버리는 것입니다.

### 3.4 듀얼 AI(Gemini × Claude) 크로스체크의 시너지
이번 전수 감사에서는 단일 모델의 편향을 방지하기 위해 상이한 아키텍처를 지닌 두 거대 모델을 교차 투입했습니다:
- **Gemini**: 전체 아키텍처의 인과관계와 불변식(ACID 트랜잭션 경계, WAL 영속성 무손실, 스냅샷 정합성)을 거시적으로 조망하고,
- **Claude**: 구석구석 숨어있는 포인터 누수, 비트 오프셋 충돌, 동시성 레이스, 침묵하는 에러(`_ = err`)를 미시적으로 집요하게 파헤쳤습니다.
한 모델이 코드를 작성할 때 가졌던 사각지대를 다른 모델이 공격적인 감사로 털어내면서, 197건이라는 방대한 결함이 누락 없이 수면 위로 드러날 수 있었습니다.

## 4. 우리가 도출한 4대 핵심 교훈

### 교훈 1: "AI가 짠 코드가 잘 돌아간다"는 말을 절대 믿지 마라
AI가 작성한 코드는 컴파일이 잘 되고, 기본 테스트를 통과하며, 겉보기에 매우 유려합니다. 하지만 그 안에는 **엣지 케이스, 동시성 인터리빙, 비트 경계값, 실패 복구 경로에 대한 '극도로 순진한(Naive) 가정'**이 숨어 있습니다. 이 순진함을 의심하지 않고 프로덕션에 직행하는 것은 시한폭탄을 배포하는 것과 같습니다.

### 교훈 2: 코딩은 가볍게 시키되, 감사는 적대적으로 쥐어짜라
AI의 진정한 강점은 새로운 코드를 마구 쏟아내는 것이 아니라, **이미 존재하는 코드에서 패턴의 모순과 락 불일치를 기계적으로 전수 대조하는 감사(Audit) 능력**에 있습니다. 개발 파이프라인에서 코드 작성보다 **"적대적 전수 감사 프롬프트"**에 더 많은 시간과 연산 자원을 배분해야 합니다.

### 교훈 3: 시스템 불변식(Invariants)을 헌법으로 명문화하라
`Invariant 7: Zero-Regex`, `Invariant 9: Zero-Truncate WAL`, `Invariant 21: Outbox Lossless Delivery`처럼, 시스템의 핵심 규칙을 자연어 헌법 수준으로 명문화하여 에이전트의 시스템 프롬프트([`GEMINI.md`](../GEMINI.md))에 박아두어야 합니다. 불변식이 명확할 때 AI는 감사 모드에서 그 규칙을 어긴 코드를 자비 없이 잡아냅니다.

### 교훈 4: TDD(Red ➔ Green ➔ Pipeline)만이 유일한 해독제다
발견된 결함을 즉시 코드로 고치려 들면, AI는 또다시 그럴듯한 땜질(Ad-hoc patch)을 덮어씌웁니다.
반드시:
1. **Red**: 결함 상황(Data Race, 데이터 증발, 패닉)을 정확히 유발하는 회귀 테스트를 먼저 작성하여 실패를 확인하고,
2. **Green**: 단일 락 캡슐화, 명시적 역직렬화 등 가장 단순하고 정석적인 해법으로 성공시키며,
3. **Pipeline**: `go test -race` 100% 통과와 3대 바이너리 컴파일을 거치는 3단계 파이프라인을 엄수해야만 코드베이스가 진짜 프로덕션 수준으로 정제됩니다.

## 5. 맺음말: 진정한 1.0 프로덕션을 향하여

LionSQL 1.0 프로젝트에서 우리가 마주한 P0 결함들은 부끄러운 실수가 아니라, **AI와 인간이 대규모 소프트웨어를 만들어갈 때 필연적으로 거쳐야 하는 성장의 증거**입니다.

코드를 짤 때의 순진함에 실망할 필요도 없고, 감사를 할 때의 날카로움에 자만할 필요도 없습니다. 
중요한 것은 **"인간 엔지니어가 아키텍처의 중심을 잡고, AI의 생성 맹점을 이해하며, 적대적 감사와 TDD 파이프라인을 통해 그 맹점을 완벽하게 통제하는 개발 문화"**입니다.

지금 하나씩 확인하고 고쳐나가는 이 시간은 결코 느린 것이 아닙니다. 
우리는 지금 **"겉보기만 멀쩡한 데모 소프트웨어"를 "어떤 가혹한 환경에서도 죽지 않는 진짜 상용 데이터베이스 엔진"으로 담금질**하고 있습니다.
