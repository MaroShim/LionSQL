## 2. 결함별 상세 메커니즘 및 원인 분석

### 2.1. [결함 1] `DEFECT-INLJ-NULL-KEY-SCAN-1`: Index Nested Loop Join NULL 인덱스 스캔
- **코드 위치**: [`pkg/execution/join.go:668-684`](file:///Users/maro/Projects/SQLion/pkg/execution/join.go#L668-L684) (`IndexNestedLoopJoinIterator.nextTuple`)
- **현상 및 메커니즘**:
  - `outerTuple`에서 조인 키를 추출할 때 `keyVal, found := lookupVal(outerTuple, n.leftKey)` 검사 시 `keyVal == nil`만 체크함.
  - 만약 `keyVal`이 `storage.Value{IsNull: true}` 인터페이스로 래핑되어 있거나 `toStorageValFromAny(keyVal)`의 결과가 `IsNull`인 경우, 이를 사전에 거르지 않고 `n.tx.IndexScan(..., &stVal, &stVal)`를 호출함.
  - WiredTiger 보조 인덱스는 `\x00NULL` 키를 물리적으로 색인하므로, 외부 테이블의 NULL 키가 내부 테이블의 NULL 인덱스 엔트리와 일치하여 `NULL = NULL`로 조인 결과에 매칭되는 심각한 관계대수 3VL 위배가 발생함.
- **조치 방안**:
  - `toStorageValFromAny(keyVal)` 직후 `stVal.IsNull` 또는 `stVal.IsNullValue()` 여부를 판별하여, NULL일 경우 인덱스 검색을 시작하지 않고 즉시 스킵(또는 LEFT JOIN 시 NULL 패딩) 처리.

### 2.2. [결함 2] `DEFECT-PGWIRE-EXT-EMPTY-COL-DROP-1`: PGWire Extended 프로토콜 후속 결과셋 유실
- **코드 위치**: [`pkg/wire/server.go:1947-1957`](file:///Users/maro/Projects/SQLion/pkg/wire/server.go#L1947-L1957) (`Server.handleExecute`)
- **현상 및 메커니즘**:
  - 다중 문장 프로시저나 배치 실행 후 `portal.Result` 체인(`res.Next`)이 생성되었을 때, 첫 번째 결과셋이 DDL/DML 등 무컬럼(`len(res.Columns) == 0`)이면 다음 블록이 실행됨:
    ```go
    if len(res.Columns) == 0 {
        if portal.Statement != nil {
            portal.Statement.NoData = true
        }
        _ = WriteCommandComplete(conn, formatPgCommandComplete(cmd, res.RowsAffected, len(res.Rows)))
        return
    }
    ```
  - 즉, 뒤에 연결된 유효한 SELECT 결과셋(`res.Next`)이 존재하더라도 이를 확인하거나 순회하지 않고 즉시 함수를 리턴하여, 클라이언트에게 후속 결과셋이 영구 유실됨.
- **조치 방안**:
  - 무컬럼 결과셋 완료 후 `res.Next`가 존재하면 다음 결과셋으로 포인터를 전진시켜 후속 결과가 클라이언트로 정상 스트리밍되도록 파이프라인 개편.

### 2.3. [결함 3] `DEFECT-DECIMAL-TO-BIGINT-ROUNDING-1`: Decimal 정수 변환 시 반올림 오류
- **코드 위치**: [`pkg/storage/decimal.go:456-462`](file:///Users/maro/Projects/SQLion/pkg/storage/decimal.go#L456-L462) (`Decimal.Int64()`)
- **현상 및 메커니즘**:
  - `Decimal.Int64()` 메서드가 `rescaled := d.Rescale(0)`을 호출함.
  - 그러나 `Rescale()` 내부(Line 368~379, 414~430)는 `twoRem.Cmp(absDivisor) >= 0` 검사를 통해 **Half-Up Rounding (사사오입 반올림)**을 수행함.
  - 결과적으로 `CAST(1.9 AS BIGINT)` 또는 `CAST(1.5 AS BIGINT)` 수행 시 `1`이 아닌 `2`로 왜곡 변환되어 ANSI SQL / T-SQL 표준의 소수점 절사(Truncation towards zero) 규격을 정면 위배함.
- **조치 방안**:
  - `Decimal.Int64()` 또는 정수 캐스팅 전용으로 반올림 없는 순수 몫(Quotient Truncation, `big.Int.Quo`) 절사 메서드(`TruncateInt64()`) 구현 및 교체.

### 2.4. [결함 4] `DEFECT-SELECT-TOP-PERCENT-DISTINCT-1`: TOP PERCENT와 DISTINCT 실행 순서 역전
- **코드 위치**: [`pkg/engine/sqlexec_select.go:237-249`](file:///Users/maro/Projects/SQLion/pkg/engine/sqlexec_select.go#L237-L249)
- **현상 및 메커니즘**:
  - 쿼리 실행기 파이프라인에서 237행 `IsTopPercent` 슬라이싱을 247행 `qInfo.Distinct` 중복 제거보다 먼저 수행함:
    ```go
    if qInfo.IsTopPercent && qInfo.LimitCount >= 0 {
        effectiveLimit := int64(math.Ceil(float64(len(rows)) * float64(qInfo.LimitCount) / 100.0))
        if effectiveLimit < int64(len(rows)) {
            rows = rows[:effectiveLimit]
        }
    }
    if qInfo.Distinct {
        rows, values = deduplicateRowsAndValues(rows, values)
    }
    ```
  - 관계대수 표준 순서상 `DISTINCT`로 유일 튜플을 확정한 뒤 상위 N%를 취해야 하나, 중복이 포함된 전체 행 기준으로 먼저 잘라낸 후 중복을 제거하므로 결과 행 수가 목표 백분율보다 심각하게 줄어듦.
- **조치 방안**:
  - `qInfo.Distinct` 평가 및 `deduplicateRowsAndValues`를 `qInfo.IsTopPercent` 절단보다 앞서 실행하도록 파이프라인 순서 재배치.

### 2.5. [결함 5] `DEFECT-SESSION-VAR-COERCE-SILENT-1`: 세션 변수 타입 변환 실패 묵인
- **코드 위치**: [`pkg/engine/session.go:170-204, 216-276`](file:///Users/maro/Projects/SQLion/pkg/engine/session.go#L170-L204)
- **현상 및 메커니즘**:
  - `DECLARE @x INT` 후 `SET @x = 'invalid_number'` 실행 시, `CoerceAndSetVarLocked`가 `coerceAnyToDataType`를 호출함.
  - `coerceAnyToDataType`는 에러(`error`)를 반환할 수 없는 구조이며, `strconv.ParseInt` 실패 시 `default: return val`로 원본 문자열을 그대로 반환함.
  - 결과적으로 정수형 세션 변수에 임의의 문자열이 무음 대입되고 사용자에게 어떠한 오류도 통보되지 않아 `[RULE:ExplicitError]`를 위반함.
- **조치 방안**:
  - `coerceAnyToDataType`가 `(any, error)`를 반환하도록 리팩토링하고, 변환 불가 시 `ErrInvalidDataType` 또는 SQL 변환 오류를 반환하여 쿼리 실패 처리.

### 2.7. [결함 7] `DEFECT-HOT-PLANCACHE-ERROR-MASKING-1`: Hot PlanCache 실행 에러 은폐
