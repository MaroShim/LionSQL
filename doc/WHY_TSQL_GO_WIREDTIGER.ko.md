# LionSQL 기초 삼총사: T-SQL, Go, WiredTiger의 전략적 융합

> - **최초 작성일**: 2026-10-18
> - **최종 수정일**: 2026-11-06

## 1. 개요 (Executive Overview)

> *"이 프로젝트의 궁극적인 성능과 경쟁력은 후반부의 마이크로 최적화가 아니라, 첫날 선택된 T-SQL, Go, WiredTiger라는 기초 기술 스택에 의해 태생적으로 결정되었다."*

소프트웨어 시스템의 구조적 수명과 시장 경쟁력은 개발 후반부의 잔손질로 결정되지 않습니다. 엔진의 한계선은 프로젝트 첫날 선택한 **기초 기술 스택(Foundational Technology Stack)**에 의해 이미 확정됩니다.

LionSQL 고유의 시장 정체성과 극단적인 트랜잭션 성능은 역사적으로 서로 다른 영역에 속해 있던 3대 기술의 의도적 융합에서 탄생했습니다:
1. **엔터프라이즈 절차형 언어 (T-SQL)**
2. **현대적 동시성 시스템 런타임 (Go)**
3. **락 프리, 제로 버큠(Zero-Vacuum) 스토리지 엔진 (WiredTiger)**

본 문서는 왜 이 기초 삼총사(Foundational Triad)를 채택했는지, 전통적인 오픈소스 관계형 데이터베이스들이 30년간 겪어온 구조적 한계를 어떻게 해결했는지, 그리고 잠재적 기술적 우려를 어떠한 엔지니어링 완화책으로 극복했는지를 체계적으로 기록합니다.

## 2. 3대 핵심 기반 (The Three Foundational Pillars)

```
                     +------------------------------------------+
                     |                LionSQL 1.0               |
                     |      (단일 독립형 정적 실행 바이너리)    |
                     +------------------------------------------+
                                          │
         ┌────────────────────────────────┼────────────────────────────────┐
         ▼                                ▼                                ▼
[ 1. T-SQL 절차형 가상머신 ]      [ 2. WiredTiger 코어 ]           [ 3. Go 런타임 & 통신망 ]
- 30년 Sybase/MSSQL 계보        - Zero-Vacuum & Zero Bloat       - 단일 정적 바이너리 (<100MB)
- VDBE 레지스터 가상머신         - Hazard Pointer 락 프리 B+Tree  - 10,000+ 고루틴 세션 풀러
- Zero RTT (스토리지 인접 실행)  - 엄격한 ACID & 16,800+ TPS      - 내장 웹 스튜디오 & REST
```

### 기둥 1: T-SQL (Sybase 이래 30년간 검증된 절차형 트랜잭션)
- **오픈소스 RDBMS 진영의 공백**:
  - **SQLite**: 저장 프로시저(Stored Procedure) 런타임이 전혀 존재하지 않음.
  - **MySQL**: 제어문과 커서 실행 속도가 악명 높게 느리고 불안정하여 복잡한 비즈니스 트랜잭션 구현에 부적합함.
  - **PostgreSQL (PL/pgSQL)**: 번잡한 따옴표 문법(`$$ ... $$`)과 린 바이트코드 VM이 아닌 AST 트리 워킹 인터프리터 구조로 인해 절차형 실행 속도에 물리적 한계가 존재함.
- **T-SQL의 핵심 가치**:
  - 지난 30년간 글로벌 금융, ERP, 결제 게이트웨이, 공급망의 미션 크리티컬 워크로드는 Sybase와 Microsoft SQL Server의 **T-SQL(`IF...ELSE`, `TRY...CATCH`, `@table` 테이블 변수, `INSERTED`/`DELETED` 가상 델타 테이블)**을 사실상의 표준으로 사용해 왔습니다.
  - **네트워크 왕복 시간 완전 제거 (Zero RTT)**: 현대 웹 애플리케이션과 ORM은 단 하나의 비즈니스 트랜잭션을 처리하기 위해 TCP 네트워크를 통해 10~20회의 SQL 왕복 질의를 전송합니다. 반면 물리 스토리지 바로 옆에서 단 한 번의 프로시저 호출(VDBE 바이트코드 <10µs)로 트랜잭션 전체를 완결하는 방식은 물리적으로 가장 빠른 컴퓨팅 패턴입니다.
  - LionSQL은 SQLite VDBE 스타일의 네이티브 레지스터 바이트코드 가상머신 위에서 T-SQL을 직접 구동하는 **세계 유일의 독립형 오픈소스 데이터베이스 엔진**입니다.

### 기둥 2: WiredTiger (30년 스토리지 딜레마의 해결)
- **대체 스토리지 아키텍처의 한계**:
  - **LSM-Tree (RocksDB, Pebble, Badger)**: 백그라운드 컴팩션 부채로 인한 주기적인 쓰기 지연(Stall) 및 꼬리 지연시간(p99) 폭증, 높은 쓰기 증폭(Write Amplification).
  - **단일 작성자 B+Tree (SQLite, BoltDB)**: 굵은 전역 쓰기 락으로 인해 최신 멀티코어 NVMe 하드웨어 병렬 대역폭의 10% 미만만 활용 가능.
  - **PostgreSQL Heap 스토리지**: 갱신된 행을 데드 튜플(Dead Tuple)로 디스크 블록에 계속 추가하여 심각한 테이블 팽창(Bloat)을 유발하고, 주기적 Autovacuum으로 치명적인 I/O 폭풍을 초래함.
- **WiredTiger의 혁신적 돌파구**:
  1. **Zero-Vacuum & Bloat-Free MVCC**: 다중 버전 업데이트 체인(`WT_UPDATE`)을 RAM에서만 유지합니다. 체크포인트 플러시 및 캐시 조정(Reconciliation) 시점에 만료된 구버전은 메모리에서 즉시 가지치기(Pruning)되어 디스크에는 오직 최신 유효 커밋 상태만 기록됩니다. 따라서 백그라운드 `VACUUM` 데몬이라는 개념 자체가 엔진에 존재하지 않습니다.
  2. **Hazard Pointer 락 프리 B+Tree**: 전역 스레드 락 없이 멀티코어 하드웨어를 포화 상태까지 확장하여 일반 상용 서버 단일 노드에서 초당 16,800회 이상의 ACID 쓰기 트랜잭션을 유지합니다.
  3. **MongoDB 엔터프라이즈 환경에서 단련된 내구성**: 10년 이상 페타바이트 규모의 프로덕션 클러스터에서 실전 검증되어 출시 첫날부터 스토리지 내구성과 크래시 복구를 보장합니다.

### 기둥 3: Go (동시성 인프라 & 자율형 단일 바이너리)
- **C/C++ 및 Rust 대비 탁월한 생산성과 이식성**:
  - C/C++ 특유의 메모리 오염 위험, 세그멘테이션 폴트, 취약한 CMake/동적 라이브러리 의존성을 배제합니다.
  - Rust의 차용 검사기(Borrow Checker)로 인한 컴파일 병목 없이 빠른 컴파일 주기와 네이티브 동시성 런타임을 제공합니다.
- **자율형 올인원 시스템**:
  - **내장 고루틴 연결 풀러**: 경량 Go 채널과 워커 풀을 활용하여 외부 사이드카(PgBouncer 등) 없이 10,000개 이상의 동시 클라이언트 연결을 직접 처리합니다.
  - **외부 데몬 의존성 제로**: 브라우저 기반 Web Studio 대시보드(`embed.FS`), REST CRUD API, 실시간 SSE 스트리머, cron 스케줄러, 트랜잭션 메일러를 하나의 독립 정적 바이너리로 통합 패키징합니다.

## 3. 핵심 비판과 엔지니어링 완화책 (Counterarguments & Mitigations)

철저한 아키텍처 평가는 회의론과 트레이드오프를 정면으로 검증해야 합니다:

| 비판 및 회의론 | 내재된 시스템 위험 | LionSQL 엔지니어링 대응 및 완화책 |
| :--- | :--- | :--- |
| **"Go 가비지 컬렉션(GC) 및 CGo 오버헤드"** | - GC 정지로 인한 꼬리 지연(p99) 스파이크<br>- CGo 스택 전환 비용 (호출당 50~100ns) | - **Zero-Allocation 핫 패스**: `sync.Pool` 레지스터 재활용, 1,024행 Volcano 청크 배치(P-12), `LazyTuple` 지연 역직렬화(P-2)로 핫 패스 힙 할당을 근절함.<br>- **커서 풀링(P-8)**: 세션 고정 `WT_CURSOR` 재활용으로 CGo 호출 비용을 894ns(초당 113만 회 OPS)까지 단축함.<br>- 나노초 단위 순수 RAM 워크로드를 위해 Pure-Go In-Memory OCC (`-engine=memory`) 엔진을 기본 내장함. |
| **"WiredTiger는 Key-Value 저장소일 뿐 관계형 엔진이 아니다"** | - 인덱스, 관계형 조인, 비용 기반 최적화기(CBO)를 애플리케이션 코드로 구현해야 하는 부담 | - LSM 컴팩션 부채와 PostgreSQL Vacuum 지옥에서 벗어나기 위해 치러야 할 합리적인 트레이드오프임.<br>- Selinger 동적 프로그래밍 조인, 64-버킷 등깊이 히스토그램 CBO, Volcano 반복자 파이프라인을 Go 코어로 직접 수직 통합함. |
| **"저장 프로시저(T-SQL)는 구시대의 유물이다"** | - 현대적인 ORM 중심 워크플로우와의 괴리<br>- Git 기반 스키마 버전 관리의 불편함 인식 | - 초당 수만 건을 처리하는 고빈도 금융/트랜잭션 도메인에서 Zero-RTT 저장 프로시저는 여전히 대체 불가능함.<br>- 최신 웹 편의성을 위해 일급 REST CRUD 엔드포인트와 JS/TS SDK를 기본 제공하여 웹 편의성과 원시 성능을 통합함. |
| **"듀얼 아키텍처로 인한 인지적 복잡성"** | - 듀얼 스토리지, 듀얼 파서, 듀얼 통신 프로토콜로 인한 유지보수 부담 | - **상호 보완적 안전망(Safety Net)**: 서브마이크로초 속도의 Pratt 파서 뒤에 ANTLR4 100% 완전 파서 백업; 즉각적인 인메모리 테스트/서버리스용 OCC 뒤에 엔터프라이즈 NVMe 내구성용 WiredTiger 백업. |

## 4. 독보적인 융합: PostgreSQL 통신 프로토콜을 통한 T-SQL 저장 프로시저 구동

LionSQL의 가장 매력적인 기술적 교차점은 **PostgreSQL 와이어 프로토콜(포트 :5433)과 T-SQL 절차형 가상머신의 매끄러운 결합**입니다:

- 전 세계 개발자와 프레임워크는 기존에 사용하던 표준 도구(`psql`, DBeaver, TablePlus, Beekeeper Studio) 및 언어 드라이버(`pgx`, GORM, Prisma, psycopg2, Npgsql)를 통해 포트 `5433`으로 즉시 연결합니다.
- 복잡하고 까다로운 PostgreSQL PL/pgSQL 대신, **성숙하고 표현력이 뛰어난 T-SQL 저장 프로시저, 트리거, 테이블 변수**를 호출하며, VDBE 바이트코드를 통해 마이크로초 단위로 실행됩니다.
- 이 크로스 프로토콜 브리지는 PostgreSQL의 범용 생태계 접근성과 Microsoft SQL Server 절차형 런타임의 트랜잭션 능력을 동시에 누리는 독보적인 가치를 제공합니다.

## 5. 결론: 100MB 미만 단일 정적 바이너리의 완결성

> *"완벽함이란 더 이상 보탤 것이 없을 때가 아니라, 더 이상 뺄 것이 없을 때 완성된다."*

LionSQL은 외부 운영 복잡성을 단호히 거부합니다. JVM, Python, Node.js, Nginx 리버스 프록시, PgBouncer 커넥션 멀티플렉서, 외부 크론 데몬이 전혀 필요하지 않습니다:

- **관계형 데이터베이스 커널**
- **듀얼 통신 프로토콜 리스너 (:5433 PGWire, :1433 TDS)**
- **WiredTiger 락 프리 B+Tree MVCC 스토리지 엔진**
- **VDBE T-SQL 바이트코드 가상머신**
- **임베디드 웹 관리 스튜디오 (:8090)**
- **네이티브 고루틴 커넥션 풀러 & 크론 스케줄러**

이 모든 핵심 기능이 **100MB 미만의 단일 독립 정적 실행 파일(`bin/lionsql`)** 하나에 완전히 집약되어 있습니다.

프로젝트 시작 첫날 선택했던 **T-SQL, Go, WiredTiger**의 기반이 구조적으로 견고했기 때문에, LionSQL은 타협 없는 자율형 프로덕션 데이터베이스 엔진으로 자리잡았습니다.
