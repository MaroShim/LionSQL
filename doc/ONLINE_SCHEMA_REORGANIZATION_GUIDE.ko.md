> - **문서 ID**: `GUIDE-SCHEMA-REORG-1`
> - **버전**: `v0.92.0`
> - **최종 갱신일**: 2026-11-12
> - **대상 독자**: 데이터베이스 관리자(DBA), 백엔드 시스템 엔지니어, DevOps 엔지니어

## 1. 개요 및 스키마 진화 철학

엔터프라이즈 환경에서 데이터베이스 스키마는 비즈니스 요구사항에 따라 지속적으로 변화합니다. 그러나 가동 중인 프로덕션 데이터베이스에서 테이블 구조를 변경하는 작업은 잘못 수행될 경우 배타적 테이블 락(Exclusive Lock), 쿼리 스톨(Stalls), 복제 지연 및 데이터 불일치를 유발할 수 있습니다.

LionSQL은 **단일 정석 V2 바이너리 튜플 코덱(`0x02`)**을 바탕으로 예측 가능하고 안전한 스키마 진화(Schema Evolution) 메커니즘을 제공합니다:
1. **컬럼 추가(`ADD COLUMN`)**: 락과 디스크 재작성 없이 **메타데이터 갱신만으로 $O(1)$에 즉시 완료**됩니다.
2. **컬럼 삭제(`DROP COLUMN`)**: 맨 끝(Tail) 컬럼은 $O(1)$ 즉시 삭제를 지원하며, 서비스 가용성을 파괴하는 **위험한 런타임 중간 컬럼 삭제는 Fail-Closed(`ErrDropColumnNotTail`)로 사전에 방어**합니다.
3. **대규모 구조 개편**: 무중단·무재시작 **Copy-and-Switch** 표준 절차를 통해 안전하게 수행합니다.

## 2. 컬럼 추가 (ADD COLUMN) — Instant DDL과 DEFAULT의 정석

### 2.1. 과거 레거시 RDBMS 시절의 딜레마: "DEFAULT를 주면 DB가 멈춘다?"
과거 레거시 RDBMS(오라클 10g 이전, MySQL 5.7 이전, PostgreSQL 10 이전) 환경에서는 다음과 같은 성능 재앙이 존재했습니다:
- `ALTER TABLE tbl ADD col INT DEFAULT 0 NOT NULL;`을 실행하면, 엔진이 수천만 건의 기존 디스크 레코드를 일일이 읽어 실제로 `0`을 채워 넣는 **물리적 전수 재작성(Full Table Rewrite)**을 감행했습니다.
- 이로 인해 수 시간 동안 테이블에 배타적 락(X-Lock)이 걸려 서비스가 마비되었고, 현장 DBA들은 *"DEFAULT를 주지 말고 일단 NULL 허용으로 컬럼만 빠르게 추가한 뒤, 야간에 배치 스크립트로 1만 건씩 분할 UPDATE를 쳐라"*라는 회피책을 강제당했습니다.

### 2.2. 현대 Instant DDL (LionSQL V2 튜플)의 아키텍처 혁신
LionSQL(및 SQL Server 2012+, PostgreSQL 11+, MySQL 8.0)에서는 **Instant ADD COLUMN** 기술이 완성되면서 이 딜레마가 근본적으로 소멸되었습니다.

```
[디스크의 기존 물리 튜플]  ───▶  [LionSQL V2 튜플 디코더]  ───▶  [어플리케이션 계층]
(encodedCols = 3)               "스키마 컬럼 수 N = 4 감지"
                                4번째 신규 컬럼은 디스크 수정 없이
                                스키마 메타데이터의 DEFAULT 'ACTIVE'를
                                메모리에서 온더플라이로 즉시 패딩! ($O(1)$)
```

- **디스크 I/O 0바이트**: 기존 디스크 레코드를 단 1바이트도 건드리지 않고, 카탈로그 메타데이터에 컬럼 정보와 기본값(`col.Default`)만 기록한 후 **0.001초 만에 완료($O(1)$)**됩니다.
- **온더플라이(On-the-fly) 메모리 패딩**: 튜플 디코더(`DecodeTupleToRowWithArena`)가 이전 스키마로 기록된 과거 레코드를 읽어낼 때, 물리 바이트에 없는 꼬리 컬럼을 메타데이터의 `DEFAULT` 값(또는 `NULL`)으로 즉시 가상 합성하여 반환합니다.

### 2.3. 현대적 모범 사례 (Best Practice): DEFAULT를 지정해야 하는 결정적 이유
성능 부담(테이블 락 및 디스크 재작성)이 완전히 제거된 현대 환경에서는, **어플리케이션 안정성과 데이터 무결성을 위해 명시적인 DEFAULT 값을 지정하는 것이 명백한 모범 사례**입니다:

1. **어플리케이션 널 포인터(NPE) 및 역직렬화 패닉 방지**:
   - 신규 컬럼에 무분별하게 `NULL`이 허용되면, 기존 백엔드 코드(Java, Go, C#, Python)에서 `null` 체크 누락으로 인한 런타임 크래시나 역직렬화 에러가 발생합니다.
   - 예: `status` 컬럼 추가 시 `DEFAULT 'ACTIVE'`를 지정하면 기존 코드가 아무런 수정 없이도 완벽한 하위 호환성을 유지합니다.
2. **SQL 삼치 논리(Three-Valued Logic, 3VL) 왜곡 차단**:
   - SQL 표준에서 `NULL`은 비교 연산 시 `UNKNOWN`으로 처리됩니다. `WHERE status <> 'CANCELLED'` 같은 조건에서 `NULL`인 행들이 조회 결과에서 완전히 누락되는 비즈니스 로직 왜곡을 방지합니다.
3. **`NOT NULL` 무결성 제약의 즉시 적용 가능**:
   - 데이터가 이미 적재된 테이블에 `NOT NULL` 제약을 가진 컬럼을 추가하려면 문법적·논리적으로 반드시 `DEFAULT`가 존재해야만 즉시 성립합니다.

### 2.4. 주의해야 할 단 하나의 예외: 비결정적(Non-Deterministic) 기본값
- **안전한 상수 기본값 ($O(1)$ Instant)**:
  - `DEFAULT 0`, `DEFAULT 'ACTIVE'`, `DEFAULT '1970-01-01'` 등 고정된 리터럴 값. 메타데이터에 단 1회 기록되므로 100% 안전합니다.
- **주의 대상 (행마다 고유 값이 필요한 경우)**:
  - `DEFAULT NEWID()`나 `DEFAULT UUIDV7()`처럼 행마다 서로 다른 고유 식별자가 생성되어야 하는 비결정적 기본값은 메타데이터 하나로 표현할 수 없으므로 행별 물리 생성이 불가피합니다.

## 3. 컬럼 삭제 (DROP COLUMN) — Tail 컬럼 $O(1)$과 중간 컬럼 안티패턴

### 3.1. 맨 끝(Tail) 컬럼의 $O(1)$ 즉시 삭제 원리
테이블의 맨 끝에 위치한 마지막 컬럼(Tail Column)의 삭제는 물리 레코드의 오프셋을 어떠한 형태로도 뒤흔들지 않습니다. LionSQL의 튜플 디코더는 이전 튜플의 물리 바이트 중 초과된 꼬리 부분만 무시하면 되므로, **메타데이터 갱신만으로 $O(1)$에 안전하게 즉시 완료**됩니다.

```sql
-- 마지막(Tail) 컬럼 삭제: O(1) Instant 완료
ALTER TABLE customers DROP COLUMN legacy_memo;
```

### 3.2. 런타임 중간 컬럼 삭제의 운영상 안티패턴
반면, 가동 중인 프로덕션 데이터베이스에서 테이블의 중간 컬럼(Non-Terminal / Middle Column)을 `ALTER TABLE ... DROP COLUMN`으로 직접 삭제하는 행위는 다음과 같은 치명적인 위험을 내포하는 **대표적인 운영상 안티패턴(Operational Anti-Pattern)**입니다.

1. **배타적 테이블 락 및 쓰기 스톨(Lock Contention & Write Stalls)**:
   물리적인 전수 재작성을 수행할 경우, 수백만~수천만 건의 데이터를 보유한 테이블에서 긴 시간 동안 배타적 락(X-Lock)이 유지되어 모든 온라인 트랜잭션이 블로킹되고 가용성 SLA가 파괴됩니다.
2. **복제 지연 및 동기화 충돌**:
   WAL/AOF 스트림에 대규모 레코드 변경이 한꺼번에 쏟아져 복제본(Replica) 노드에 심각한 복제 지연(Replication Lag)을 유발합니다.
3. **어플리케이션 및 ORM 직렬화 불일치**:
   어플리케이션 계층(ORM, struct 매핑 등)이 배포되기 전 또는 배포 도중에 컬럼 서수가 변경되면 런타임 역직렬화 에러 및 데이터 손실이 발생합니다.

### 3.3. LionSQL 엔진의 Fail-Closed 설계와 영구 Spec-Out (`PERF-OCC-INSTANT-DROP-COL-1`)
LionSQL 엔진은 중간 컬럼 삭제에 대한 두 가지 대안적 구현 방식을 모두 검토한 후 기술적 타당성에 따라 영구 배제(Spec-Out)를 확정했습니다:

- **대안 A (물리적 전수 재작성)**: 런타임 스톨 및 락 문제로 탈락.
- **대안 B (스키마 가상 결번 마스킹/Tombstone)**: 스키마에 삭제 플래그를 두고 물리-논리 컬럼 인디렉션 맵을 유지하는 방식은, 엔진 전반의 복잡도를 극도로 가중시키고 검증을 어렵게 만들 뿐만 아니라 LionSQL의 핵심 경쟁력인 **0.5ns 고정 오프셋 튜플 디코딩 핫패스 성능을 영구적으로 저하시킴**.

따라서 LionSQL은 데이터가 존재하는 테이블에서 중간 컬럼 삭제 시도 시 즉시 명시적 에러(`ErrDropColumnNotTail`)를 반환(Fail-Closed)하여 의도치 않은 장애를 사전에 방어하며, 공식 표준 대안으로 **Copy-and-Switch** 패턴을 규정합니다.

## 4. 동시성 제어(OCC / MVCC)에서의 Copy-and-Switch 동작 원리

중간 컬럼 제거 및 대규모 테이블 구조 개편을 위해 Copy-and-Switch 패턴을 진행할 때, LionSQL 엔진 내부에서 발생하는 동시성 메커니즘은 다음과 같습니다.

### 4.1. 복사 단계 (`CREATE TABLE ... AS SELECT`)에서의 무충돌 특성
- **In-Memory OCC 엔진**:
  OCC의 낙관적 동시성 제어 검증(`ErrWriteConflict`)은 **동일한 행(Row)을 동시에 수정(Update/Delete)**하려고 할 때 발생합니다. Copy 작업에서 복사 세션은 원본 테이블(`old`)을 **단순 읽기(Read)**하고, 신규 테이블(`new`)에만 **쓰기(Insert)**를 수행합니다. 따라서 원본 테이블에 수천 건의 동시 트랜잭션이 유입되더라도 복사 세션과 기존 트랜잭션 간에는 Write-Write 충돌이 전혀 발생하지 않으며 롤백되지 않습니다.
- **WiredTiger MVCC 엔진**:
  "읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다(Non-Blocking Read Committed & Snapshot Isolation)" 불변식에 따라 복사 세션은 스냅샷을 기반으로 격리된 상태에서 데이터를 읽어옵니다. 기존 트랜잭션과 데드락이나 락 대기가 발생하지 않습니다.

### 4.2. 스위칭 단계 (`ALTER TABLE ... RENAME`)에서의 무중단 특성
- **서버 재시작 불필요 (Zero-Restart)**:
  테이블 이름 변경은 디스크의 물리 파일을 옮기는 작업이 아니라, LionSQL 시스템 카탈로그 메타데이터의 포인터를 원자적으로 교체하는 $O(1)$ 연산입니다.
- **마이크로초 단위 원자적 완료**:
  트랜잭션 블록 내에서 구 테이블 이름 변경과 신규 테이블 이름 변경을 연속으로 수행하면 수 마이크로초(µs) 내에 메타데이터 스위칭이 완료되며, 연결된 클라이언트 세션들은 단절 없이 즉시 새로운 스키마로 라우팅됩니다.

## 5. 실전 운영 시나리오 및 절차

### 5.1. 표준 점검 창구(Maintenance Window) 절차 (권장)
데이터 정합성을 100% 보장하는 가장 단순하고 안정적인 엔터프라이즈 정석 절차입니다.

#### 1단계: 사전 점검 (인덱스 및 제약 조건 확인)
원본 테이블의 스키마와 인덱스 정의를 확인합니다.
```sql
-- 원본 테이블 구조 확인
DESC customers;

-- 생성된 보조 인덱스 확인
SELECT index_name, column_name FROM sys.indexes WHERE table_name = 'customers';
```

#### 2단계: 신규 테이블 생성 및 데이터 복사
제거 대상 중간 컬럼(`legacy_notes`)을 제외하고 필요한 컬럼들만 프로젝션하여 복사합니다.
```sql
-- 1. 필요한 컬럼만 추출하여 신규 테이블 생성 및 데이터 복제
CREATE TABLE customers_new AS 
SELECT 
    customer_id, 
    name, 
    email, 
    created_at 
FROM customers;
```

#### 3단계: 보조 인덱스 및 제약 조건 재구축
신규 테이블에 필요한 인덱스를 미리 생성합니다.
```sql
-- 보조 인덱스 생성
CREATE INDEX idx_customers_email ON customers_new (email);
```

#### 4단계: 원자적 메타데이터 스위칭 (Switching)
트랜잭션 블록을 통해 원본 테이블과 신규 테이블을 원자적으로 맞교환합니다.
```sql
BEGIN TRANSACTION;
    -- 원본 테이블을 백업 테이블로 이름 변경
    ALTER TABLE customers RENAME TO customers_backup_20261112;

    -- 신규 테이블을 정규 서비스 테이블로 이름 변경
    ALTER TABLE customers_new RENAME TO customers;
COMMIT;
```

#### 5단계: 검증 및 사후 정리
어플리케이션 쿼리가 정상 작동하는지 확인한 후, 일정 유예 기간(예: 1주일)이 지나면 백업 테이블을 안전하게 제거합니다.
```sql
-- 정상 라우팅 검증
SELECT COUNT(*) FROM customers;

-- 유예 기간 경과 후 안전한 백업 테이블 삭제
DROP TABLE customers_backup_20261112;
```

### 5.2. 대용량 테이블 청크(Chunk) 분할 복사 기법
수천만 건 이상의 대용량 테이블인 경우, 단일 `CREATE TABLE ... AS SELECT` 실행 시 발생할 수 있는 메모리 버퍼 및 캐시 부담을 완화하기 위해 기본 키(Primary Key) 범위별 청크 단위 분할 복사를 권장합니다.

```sql
-- 1. 신규 테이블 스키마만 생성 (빈 테이블)
CREATE TABLE orders_new (
    order_id INT PRIMARY KEY,
    customer_id INT,
    total_amount DECIMAL(18,2),
    created_at DATETIME
);

-- 2. 범위별 청크 복사 반복 (예: 100,000건 단위)
INSERT INTO orders_new SELECT order_id, customer_id, total_amount, created_at 
FROM orders WHERE order_id >= 1 AND order_id < 100000;

INSERT INTO orders_new SELECT order_id, customer_id, total_amount, created_at 
FROM orders WHERE order_id >= 100000 AND order_id < 200000;

-- 3. 복사 완료 후 보조 인덱스 생성 및 스위칭 트랜잭션 수행
BEGIN TRANSACTION;
    ALTER TABLE orders RENAME TO orders_old;
    ALTER TABLE orders_new RENAME TO orders;
COMMIT;
```

### 5.3. 24/7 고가용성 환경에서의 델타(Delta) 동기화 전략
서비스 다운타임 없이 지속적으로 쓰기 트랜잭션이 발생하는 환경에서는 복사가 진행되는 동안 유입된 변경분을 보정해야 합니다.

```
[클라이언트 트래픽] ───────────────┐
                                │
                                ▼
                    ┌───────────────────────────┐
                    │     원본 테이블 (old)      │
                    └─────────────┬─────────────┘
                                  │
         ┌────────────────────────┴────────────────────────┐
         │ 1. 초기 스냅샷 대량 복사 (Bulk Copy)             │ 2. 복사 중 발생한 델타
         ▼                                                 ▼
┌───────────────────────────┐                     ┌───────────────────────────┐
│     신규 테이블 (new)      │ ◄── [증분 동기화] ── │    CDC / 변경 로그 큐     │
└───────────────────────────┘                     └───────────────────────────┘
         ▲
         │ 3. 델타 최종 수렴 후 원자적 RENAME 스위칭 ($O(1)$)
```

1. **초기 스냅샷 복사 시작 시점 기록**:
   복사 시작 시점의 LSN(Log Sequence Number) 또는 타임스탬프 $T_0$를 확보합니다.
2. **초기 데이터 복사 진행**:
   $T_0$ 이전의 데이터를 신규 테이블로 적재합니다.
3. **증분 델타 동기화 (Catch-up)**:
   $T_0$ 이후에 원본 테이블에 반영된 INSERT/UPDATE/DELETE 이벤트를 신규 테이블에 리플레이하여 정합성을 일치시킵니다.
4. **최종 컷오버(Cutover)**:
   델타 차이가 0에 수렴한 시점에서 트랜잭션을 통해 `ALTER TABLE ... RENAME` 스위칭을 수행합니다.

### 6.2. 자주 묻는 질문 (FAQ)
#### Q1. 복사 중에 원본 테이블에 다른 사용자의 쓰기(INSERT/UPDATE)가 발생하면 충돌로 롤백되나요?
**아닙니다.** 복사 트랜잭션은 원본 테이블에 대해 순수 읽기(Read)만 수행하고 신규 테이블에만 쓰기를 수행합니다. LionSQL의 OCC 및 WiredTiger MVCC 엔진 모두 읽기와 쓰기가 상호 블로킹되지 않으므로, 원본 테이블에 쓰기가 유입되어도 충돌(`ErrWriteConflict`)이 발생하지 않습니다.

#### Q2. 스위칭(`RENAME`) 시에 데이터베이스 프로세스를 재시작해야 하나요?
**전혀 필요 없습니다.** LionSQL의 테이블 RENAME은 카탈로그 메타데이터의 테이블 식별 포인터만 교체하는 초고속 $O(1)$ 연산입니다. 서버 프로세스 재시작 없이 무중단(Online)으로 수 마이크로초 내에 반영됩니다.

#### Q3. 마지막(Tail) 컬럼 삭제는 왜 복사 없이 즉시 삭제되나요?
마지막 컬럼(Tail Column)은 물리 레코드의 맨 끝에 위치하므로, 튜플 디코더가 뒤쪽 바이트를 단순히 무시하기만 하면 됩니다. 따라서 스키마 메타데이터 갱신만으로 $O(1)$ 즉시 안전하게 완료됩니다.

## 7. 결론

프로덕션 환경에서의 테이블 스키마 진화는 단순한 DDL 문법 지원의 문제가 아니라 서비스의 무중단 가용성과 데이터 무결성을 보장해야 하는 운영 엔지니어링의 핵심 영역입니다:
1. **컬럼 추가(`ADD COLUMN`)**: 락과 디스크 재작성 없는 **Instant $O(1)$ DDL**로 즉시 완료되며, 어플리케이션의 안정성을 위해 **상수 `DEFAULT` 값을 적극 지정하는 것**이 현대 엔터프라이즈의 표준 정석입니다.
2. **중간 컬럼 삭제(`DROP COLUMN`)**: 위험한 런타임 중간 컬럼 삭제는 **Fail-Closed(`ErrDropColumnNotTail`)로 사전에 방어**하며, 정석적인 **Copy-and-Switch** 절차를 통해 무중단·무재시작 스키마 전환을 달성합니다.
